# 员工端小程序产品化差距诊断

> 出具日期：2026-11-07 ｜ 基线：`main` 分支 `d69fe4f`
> 性质：**只读评审报告**。本轮未修改任何 `.js / .wxml / .wxss / .json / .sql`，未执行 DDL，未重启服务。
> 触发：用户质疑「工作人员小程序页怎么是 SaaS 网页的逻辑」「我的页面都没有」「你又不是每个岗位一直只有一个人」「没有底部导航栏，我的 啥都没有」。
> 2026-11-07 11:26 补充核查：员工端底部导航 0 命中、客户端「我的」页多为演示弹层，见缺陷 2。

---

## 一、结论

三处质疑指向**同一个根因**：员工端 18 页（工作台 `home` + 17 个原型页 `c1–c6 / v1–v5 / g1–g3 / d1–d3`）是 2026-11-06 从 `pet-care-staff-ui` 的**静态 HTML 高保真原型整页搬迁**而来，转换只覆盖了语法层：

| 做了 | 没做 |
|---|---|
| HTML → WXML 标签映射（`span/b/small/i`→`text`、`h3/p`→`view`）、`<br>` 转空格 | 移除原型为「看起来像手机」自绘的假状态栏 / 假导航栏 / 假 Home 条 |
| `common.css` → `styles/staff.wxss`，px→rpx、`.staff-page` 作用域化、去 `:has()` / `:not()` | 清理桌面 CSS 属性（`cursor` / `user-select` / `resize` / `outline`） |
| 状态显隐改 `wx:if`、radio 字段推导修正、`<text>` 嵌块级升为 `<view>` | 小程序端信息架构：员工 tabBar / 个人中心 / 消息入口 |
| `utils/staff-page.js` 页面工厂统一 guard / 表单 / 照片 / 签名 / 提交 | 把原型里写死的演示数据换成接口数据 |
| 双层岗位鉴权（`utils/auth.js` + 后端 `security/StaffAuth`） | 把「岗位」与「具体的人」在 UI 层解耦 |

因此交付的是**流程与权限的正确性**，不是**移动端产品形态的完整度**。这是迁移时的取舍与评审遗漏，不是用户看错。

### 当时为什么没发现

迁移验收口径全部是「结构 / 接口正确性」：29 页四件套齐全与标签配对、`node --check` 34 个 JS、Node 打桩 wx + 网络 **111/111** 断言、后端 8090 六岗位接口冒烟（`GROOM→care-log` 403、`DRIVER` 跨项目核销拒绝、`VET vetReady=true`）。**没有视觉评审、没有产品逻辑评审**。29 张微信开发者工具模拟器实拍截图是 2026-11-07 才补的，补齐后问题才暴露。

`docs/项目文档.md:430` 附录 A、`:436` 更新提示已把「岗位权限 / 合规留痕」标成部分落地，但未覆盖「原型搬迁带来的产品化差距」。

## 二、三处缺陷逐条举证

### 缺陷 1：网页壳（「SaaS 网页逻辑」的直观来源）

| 证据 | 位置 |
|---|---|
| **18 / 18 个员工页 WXML** 首行均含 `<view class="statusbar"><text>9:41</text>…`、`<view class="navbar">…`、`<view class="nav-capsule">··· ◎</view>` | `pages/staff/**/*.wxml`，典型 `pages/staff/d2/d2.wxml:1` |
| 假壳样式定义齐全且为 `position:sticky`，另含 `.safe-area` / `.home-indicator` 假 Home 条 | `styles/staff.wxss:7`、`:12` |
| 各页 `.json` **本来就有**真实 `navigationBarTitleText`（18 页全有），原生导航栏一直在 | `pages/staff/*/*.json` |
| 转换后的 WXSS 残留桌面属性：`cursor:pointer` / `user-select:none` / `resize:none` / `touch-action:none` / `outline:none` | `styles/staff.wxss:7` |

结果：真小程序里系统状态栏 + 原生胶囊 + 原型画的「9:41 / ▂▄▆ ◔ ▭ / ··· ◎」三层叠在一起，顶部像网页里嵌了个手机模型。这是「SaaS 感」最直接的来源。

> 说明：原型是给浏览器看的静态页面，自绘手机壳是其**展示需要**；搬进小程序后该保留的是内容，不是外壳。

### 缺陷 2：员工端没有底部导航栏，也没有「我的」

| 证据 | 位置 |
|---|---|
| `tabBar` 三项 `pages/index/index`（首页）、`pages/orders/orders`（历史订单）、`pages/mine/mine`（我的）**全部是客户端页面** | `app.json:41`、`:48`、`:54`、`:60` |
| 员工端 grep `tabBar / tab-bar / bottom-nav / footer-nav / custom-tab-bar` → **0 命中**（全仓库唯一命中就是上面那个客户端 `app.json:41`）。小程序 tabBar 是全局配置，非 tabBar 页面不会显示底部栏，因此员工 18 页**一张都没有** | `pages/staff/**` |
| 员工端 grep `个人中心 / 账号设置 / 修改密码` → **0 命中**；`pages/staff/` 下无 `mine` / `settings` 页 | `pages/staff/**` |
| 全端唯一的身份 / 退出入口：工作台顶部一张 profile 卡（姓名、岗位、写死的「在岗」标签、3 个统计数）+ 一个「退出」按钮 | `pages/staff/home/home.wxml:3-20`、`:15`；`home.js:15`、`:71` |
| 客户端确有个人中心页（`11_客户_个人中心.png`），但与员工会话互斥，员工不可用 | `app.js` 会话互斥；`pages/mine/mine.*` |

**补充核查（2026-11-07 11:26）**：客户端 `pages/mine/mine.wxml` 并非空页——有概览卡（头像 / 姓名 / 脱敏手机号 / 编辑资料）、3 个统计（寄养中 / 已完成 / 累计寄养）、5 个菜单（我的宠物 / 优惠券 / 评价 / 联系客服 / 关于我们）、退出登录与版本号。但**其中多项是演示弹层而非真实功能**：`openProfile` 弹「演示环境暂不支持在线修改资料」，`openCoupons` / `openReviews` 共用 `showDemoModal` 演示文案，`关于我们` 里是演示地址与演示客服号。因此「我的 啥都没有」在客户端也部分成立：**有界面骨架，没有真实資料维护能力**。

结果：员工登录后直接落工作台，全端无底部导航、无个人中心、无消息 / 通知中心、无资质与排班自助查看，靠 18 个页面的返回栈串联——这是网页后台「工作台 + 二级表单页」的信息架构，不是小程序惯用形态。

#### 补底部导航的三个方案（架构决策点，未实施）

小程序 `app.json` 的 `tabBar` **全局唯一**，客户 / 员工会话互斥（`app.js`），所以不能简单「再加一组」。

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A 自定义 tabBar（推荐）** | `app.json` 设 `"tabBar": {"custom": true, "list": [...]}`，新增 `custom-tab-bar/` 组件，按当前会话渲染「客户：首页 / 历史订单 / 我的」或「员工：工作台 / 待办 / 我的」；tab 切换统一 `wx.switchTab`，客户↔员工切换用 `wx.reLaunch` 并清另一套会话 | 新建 `custom-tab-bar/*` + 员工 `mine` 页 + 员工「待办」页（或复用 `home`）；`app.json` list 需含两端全部 tab 页；18 个员工页的返回栈与 `navigateTo` 逻辑要核对 | 标准做法，两端各自有原生底部栏，视觉与交互最像小程序 |
| B 每页自绘底部条 | 员工 18 页各引一个 `.footer-nav` 组件 | 18 个 WXML 全改；与原生返回手势、假 `safe-area` 冲突；非原生 tabBar，切换需 `reLaunch` | 改动散、体验差，不推荐 |
| C 拆两个小程序 | 客户端 / 员工端各自独立 `app.json` 与 tabBar | 复制公共 `utils` / `styles`，两套发布与会话，毕设规模不划算 | 架构最干净但成本最高 |

**推荐 A**，且应先做 P0-1（去假手机壳），否则自定义 tabBar 会和原型自绘的假 `statusbar` / `home-indicator` 再次叠层。

### 缺陷 3：隐含「一岗一人」假设

| 证据 | 位置 |
|---|---|
| **写死的人名**：「门店接收人 林晓雯」；同页还写死「丰泽区东海大街 88 号」「2026-11-06 16:00」「定位偏差 12 m」「布偶猫」 | `pages/staff/d2/d2.wxml:1` |
| 硬编码原型数据分布在 **11 个员工页**：`c1 c2 c5 c6 d1 d2 d3 g3 v1 v2 v3`（命中 `林晓雯 / 丰泽区东海大街 / 定位偏差 / 2026-11-06 / 布偶猫`） | `pages/staff/**/*.wxml` |
| 工作台是 `meName / positionLabel` 单人视角 + 固定「在岗」标签，无「同岗位同事 / 班次成员 / 交接对象」概念 | `pages/staff/home/home.js:15` |
| 权限矩阵按**岗位**给页面白名单与读写模式，不按 `staff_id` / 班次区分归属 | `utils/auth.js:38`（`MODULE_MATRIX`）、`:62`（`PAGE_RULES`）、`:209`（`guard()`） |
| 页面工厂提交载荷由各页 `opts.build()` 产出，**不含 `staff_id` / 责任人**，操作人靠后端 JWT 反推 | `utils/staff-page.js:219-252` |
| 演示数据恰好一人一岗，掩盖了多人场景：`sql/schema.sql` 种子 5 个员工对应 5 个岗位；实库 `staff` 5 行、`staff_shift` 2 行（均属 `staff_id=3` 兽医）、`staff_cert` 1 行 | 运行库只读核查（2026-11-07 09:44） |

「交接对象」被写成固定人名，等于假设每个岗位永远只有那一个人；一旦同岗位多人、排班轮替或跨岗协作，签字归属就无法表达。

## 三、关键澄清：后端数据模型其实支持多人

问题**只在前端原型层**，后端已按「人」建模，改造不需要改库表结构：

| 能力 | 现状 |
|---|---|
| 一人多岗 | `staff.positions` 逗号分隔多值；`StaffAuth.normalize()` 兼容六岗位英文代码与中文旧值，空 / 未知岗位 fail closed |
| 多人同岗 | `staff.staff_id` 独立主键，岗位只是属性，不唯一 |
| 排班到人到日 | `staff_shift(staff_id, shift_date, shift_type, duty, remark)`，实库已有 2 行按 `(staff_id=3, 日期)` 记录 |
| 资质到人有有效期 | `staff_cert(staff_id, cert_type, valid_from, valid_to)`，`VET_LICENSE` |
| 执业 / 在岗判定按人 | `security/StaffAuth.java:143-157` `vetReady()` 用 `userId()` + 当日 `staff_shift` + 有效期内 `VET_LICENSE` 三重判定；`requireVet()` 无在岗兽医 fail closed，不降级给护理代签 |

即：**「一个岗位多人、一个人多岗」在数据层与鉴权层成立**，缺的是前端 UI 与聚合接口把「人」暴露出来（在岗同事、班次成员、交接对象选择、待办归属）。

## 五、答辩可用口径

可直接引用，避免把「应该做」说成「已经做」：

1. **定位**：员工端是「按岗位切分的现场作业工具集」，不是完整的员工门户。本轮交付重点是**流程与权限正确性**——18 页按 PRD §3.3 白名单逐岗位授权、读写分级、VET 执业证 + 当日在岗判定、入离店交接签字、异常复核与处置、按岗位核销、巡视幂等、前端 `guard()` 与后端 `StaffAuth` 双层校验。
2. **已知局限**：17 页由静态高保真原型迁移，保留了网页原型自绘的手机外壳与部分静态演示数据；**员工端无底部导航栏、无个人中心**（客户端「我的」页虽有骨架，编辑资料 / 优惠券 / 评价仍为演示弹层）；UI 层未展开「同岗位多人 / 一人多岗」的组织视角。这些是产品化完整度问题，不影响已实现的业务流程与权限边界。
3. **改进方向**：见第四节 P0/P1。**后端已具备按人建模条件**（`staff_id` / `positions` / `staff_shift` / `staff_cert` / `vetReady()`），改造集中在前端与聚合接口，**无需变更库表结构**。
4. **证据材料**：桌面 `护宠宝-小程序界面截图/` 的 29 张微信开发者工具模拟器实拍图（含索引页）、本报告、`docs/项目文档.md` 附录 A、上一轮 `docs/Playwright全量回归报告-2026-11-06.md`。
