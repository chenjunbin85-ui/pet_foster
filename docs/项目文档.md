## 一、项目概述

「毛球旅馆」是一套面向宠物寄养门店的全栈演示系统，覆盖三类角色：

- **门店管理员**：经营数据统计、工作人员账号与房型价位维护；可查看订单流水、导出订单。**当前没有客户与宠物档案权限**（`/api/customers`、`/api/pets` 实测 403），也导不出客户/宠物。
- **门店工作人员（前台 / 护理员）**：接待客户、登记客户与宠物档案、办理入离店、录入健康与服务记录；可导出客户/宠物。**没有经营报表权限**（`/api/stats/dashboard` 实测 403），仅首页展示「本月寄养金额」。
- **养宠客户**：微信小程序自助注册登录、选择房型日期与增值服务、下单寄养、查订单与评价。**注册接口当前被安全配置拦截（实测 401）**，实际只能用已有账号登录。

系统由三部分组成：

| 子系统 | 目录 | 技术栈 | 端口 |
| --- | --- | --- | --- |
| 后端服务 | `pet-foster-server-src/pet-foster-server` | Java 17 · Spring Boot 3 · MyBatis-Plus · MySQL 8 · Redis · JWT | 8090 |
| 客户小程序 | `pet-foster-miniprogram` | 原生微信小程序（WXML / WXSS / JS） | — |
| 工作人员/管理员 Web | `pet-foster-ui-src/pet-foster-ui` | React 19 · Vite 8 · TypeScript · Tailwind CSS 4 · shadcn/ui · Recharts | 5173（dev） |

## 二、技术架构

### 2.1 整体分层

```
客户小程序 (WeChat)  ──┐
                       ├──►  Spring Boot 后端 (REST, /api/**)  ──►  MySQL 8 (pet_foster)
工作人员 Web (React) ──┘                                       └─►  Redis (登录失败计数)
```

- 统一返回结构 `Result { code, message, data }`，`code=200` 成功，业务异常 `code=500`。
- 鉴权：JWT（实际算法 **HS512**，有效期 24 小时），密码统一 BCrypt 加密。
- 登录失败限流：基于 Redis 计数（5 次 / 5 分钟锁定），见 `LoginAttemptService`。
- 接口文档：SpringDoc OpenAPI，启动后访问 `/swagger-ui.html`。
- CORS：默认 `allowedOriginPatterns("*")`（放开全部来源），可通过环境变量 `CORS_ALLOWED_ORIGINS` 收紧。

### 2.2 后端模块划分（`com.petfoster`）

| 包 | 职责 |
| --- | --- |
| `controller` | REST 入口，分 web 端（`/api/**`）与小程序端（`/api/mp/**`） |
| `service` | 业务逻辑：登录、客户、宠物、订单、价位、健康记录、服务记录、统计 |
| `mapper` | MyBatis-Plus Mapper，对应每张数据表 |
| `entity` | 与表一一对应的实体 |
| `dto / vo` | 入参校验（Jakarta Validation） / 出参脱敏 |
| `security` | JWT 过滤器、登录用户上下文、登录失败计数 |
| `enums` | 订单状态、支付状态、支付方式、宠物性别 |
| `task` | `OrderExpireTask`：定时关闭超时未支付订单 |
| `common` | 统一 Result、分页、全局异常、业务异常 |

## 七、核心业务流程（文字描述）

### 7.1 客户注册与登录

注册页：手机号（正则 `1[3-9]\d{9}`）、6–32 位密码二次确认、勾选用户协议；后端校验手机号未占用，BCrypt 加密写入 `customer` 表（默认昵称「爱宠家长」），签发 JWT 并返回客户信息。

**当前状态：不可用。** `/api/mp/auth/register` 未在 `SecurityConfig` 放行（只放行 `/api/auth/login`、`/api/mp/auth/login`、`/health` 与 Swagger），无 token 调用实测返回 **401**。新客自助注册这一环目前走不通，只能用已有客户账号登录。

老客户登录：手机号 + 密码；连续失败 5 次触发 Redis 计数锁定 5 分钟（两个入口共用同一套计数）。

### 7.2 预订与计费

- 首页：选房型（标准间 60 / 舒适间 80 / 豪华间 120）、入离店日期、3 项增值服务、备注；页面按「晚数 = 离店 − 入住（同日按 1）× 单价」预估。
- 结算页：叠加增值服务（洗护 30 / 遛宠 20 / 接送 40），扣除优惠券后显示「实付」。
- 提交参数只有：宠物、价位档位、日期、门店、`couponId`、备注；**增值服务只以「增值服务：洗护美容」这样的文字写进备注**。
- 后端重算：`total_fee = 单日价 × (离店 − 入住 + 1)`，**不含增值服务，也不读取 `couponId`**。
- 结果：跨天订单后端比页面多算 1 天房费；增值服务选了不加价；用券不减价、券不核销。实测：舒适间 80 元、`2026-10-25 → 2026-11-05`，页面 11 晚 = 880 元，订单 12 天 = 960 元（种子订单 `FO20261025002` 即 960）。
- 此外：不做房态/库存校验，同房型同日期可重复下单；`storeId` 缺省取 1，不校验门店归属（门店表目前仅一条「杭州·西湖总店」）。

### 7.3 下单与支付

- 订单创建即置「待入店 / 已支付 / 支付方式=微信」，写支付时间与实付金额；**不写支付截止时间**。
- 小程序结算提交后直接跳「支付成功」页（展示后端订单金额），不再经过支付页。
- 支付页、15 分钟倒计时、`OrderExpireTask` 仅对「未支付」订单生效，正常链路不会产生这类订单，因此实际空转（`PAY_TIMEOUT_MINUTES` 常量亦未被调用）。
- 前台建单同一规则：创建即收款、支付方式记「微信」，现金等线下收款方式无法如实记录。
- 订单号 = `FO + yyyyMMdd + 当日计数 + 1`，无并发保护，极端并发下可能撞号。

### 7.4 入店与照护

- 入店：订单页点「确认入店」→「寄养中」。**只改状态**：不生成健康记录、不校验是否到预约日、不占房。
- 健康记录：员工在「健康记录」页手工录入（入店/观测/离店），「关联订单」为选填。
- 服务记录：喂食、遛弯、洗澡等由员工手工登记。
- 客户侧「照护动态」读 `care_record`，全仓库没有任何写入方，列表通常为空；读取不校验订单归属，可跨客户读取他人订单的照护记录。
- 健康记录与服务记录**不自动同步到小程序**（两套数据未打通）。
- 疫苗：后端把历史中文文本（如「狂犬疫苗已接种」）视为已免疫，小程序只认「已接种」或 JSON，这类宠物（如「豆豆」）在小程序被判未免疫、无法下单。

### 7.5 离店与评价

- 离店：点「确认离店」→「已完成」。不校验实际离店日期，不按实住天数补退，不生成离店健康记录。
- 评价：小程序仅对「已完成」订单展示入口；后端只校验订单归属与一单一评，**不校验订单状态**，待入店订单也可提交；评价读取不校验归属。

### 7.6 取消与退款

- 小程序：待入店 / 寄养中可取消，已支付订单置「已退款」。
- 前台：取消只改「已取消」，不回写退款状态；而前台建单时已置「已支付」，导致后台看不到退款结果。
- 协议文案「入住前 24 小时免费取消、逾期收 1 晚房费」无对应实现：没有时间判断，也没有手续费计算。
- 小程序列表只对「待入店」显示取消按钮，后端却允许「寄养中」取消。

### 7.7 门店后台与权限

- 工作人员（staff）：工作台、客户与宠物档案、订单办理（入店/离店/取消/收款）、健康记录、服务记录、客户/宠物导出。
- 管理员（admin）：经营看板、员工账号、房型价位、订单查询与订单导出；**无客户/宠物/健康/服务记录权限（403）**。
- 前端还有一层限制：`OrdersPage` 对管理员隐藏入离店与取消按钮，管理员即使能看订单列表也无法办理操作。
- 角色切换需输入目标账号密码二次校验。

### 7.8 统计与导出

- 管理员：`/api/stats/dashboard`（本月订单数按创建时间、营收按 `total_fee` 且排除已取消、订单趋势、品种分布）。
- 工作人员：首页概览改为拉 1000 条订单在前端按创建时间过滤本月，另调 `monthly-revenue`；无 dashboard 权限。
- 营收口径是「订单总额」而非实收（`paid_amount`），已退款但状态未变「已取消」的订单仍会计入。
- 导出：工作人员导客户/宠物，管理员导订单，权限互斥；管理员导不出客户/宠物。

更细的问题编号（B1–B16）与修改建议见 `docs/业务流程核查报告.md`。

## 十一、员工端小程序（角色分流与页面鉴权）

### 11.1 范围与依据

把 `pet-care-staff-ui` 的 **17 页高保真 HTML 原型**迁移为原生小程序页面，并删除旧 `staff-todo` / `staff-handover` / `staff-carelog` / `staff-incident` / `staff-redeem` 五个占位页。依据 `docs/PRD.md` 3.1 / 3.3 / 3.4 / 3.6 / 3.7、`docs/业务补齐方案.md` 11.11 / 11.12、`docs/员工端UI设计提示词.md` 的「重要业务限制」。按 PRD 3.3 与方案 11.11，**员工端与顾客端共用同一个小程序**，按岗位分流，不另起一个 App。

### 11.2 会话分流

`app.js` 同时维护客户会话 `token/customer` 与员工会话 `staffToken/staffInfo`；登录页按账号类型分流：员工账号 `setStaffSession() + clearSession()` 后跳 `/pages/staff/home/home`，客户账号 `clearStaffSession()`。`utils/api.js` 的 `staffRequest` 单独带员工 token，401 时清员工会话并回登录页。两类会话互斥，避免用客户 token 调员工接口。

### 11.3 页面级鉴权（前端第一层）

`utils/auth.js` 是员工端鉴权单一事实源：

- 六岗位代码 `OWNER/FRONT/CARE/VET/GROOM/DRIVER`，中文旧值映射，`admin` 固定 `OWNER`；空岗位、未知岗位返回空集合，**fail closed**。
- `MODULE_MATRIX`：PRD 3.3 五模块 × 六岗位的 write / read / none 矩阵。
- `PAGE_RULES`：18 个页面（工作台 + 17 原型页）的白名单与逐岗位 mode；未登记页面一律拒绝。
- `guard(page, key)`：未登录 → 登录页；空岗位 → 弹窗并清会话；无权 → 弹窗回工作台；通过则回填 `readOnly / mode / meName / positionLabel`。
- 17 页由 `utils/staff-page.js` 的 `createStaffPage()` 统一在 `onLoad` 调用 guard，避免逐页漏写；只读页提交按钮 `disabled`，`submit()` 内再判一次 `readOnly`。

典型结果：`CARE` 可进 c1–c6 + v3（只读）；`FRONT` 只能 c4（只读）/ c5 + 统一工作台，无专属工作台；`OWNER` 全 18 页可见但岗位专属页多为只读。

### 11.4 后端第二层（403 才是墙）

`security/StaffAuth.java` 归一化岗位（优先 `staff.positions`，回退 `staff.position`），`require(...)` 缺权抛 `AccessDeniedException`，`GlobalExceptionHandler` 返回可读文案，例如「当前岗位（GROOM）无此操作权限，需要「CARE 或 VET 或 OWNER」岗位」。控制器类统一 `@PreAuthorize("hasAnyRole('STAFF','ADMIN')")`。

- `vetReady()` = 岗位 `VET` + `staff_cert` 有效期内 `VET_LICENSE` + `staff_shift` 当日班次；评估签署、异常处置、隔离/送医授权均走 `requireVet()`。`OWNER` 紧急兜底记 `emergency` 路径，但异常保持未闭环、要求 24 小时内 VET 补签。
- 字段级限制：`CARE` 只上报异常描述、不落医疗定级；核销按岗位锁定项目（`CARE` 遛宠 / `GROOM` 洗护 / `DRIVER` 接送）；未签离店评估时阻断离店交接；巡视按 `(order_id, log_date, shift)` 幂等覆盖（弱网重试不产生重复记录）。

## 附录 A、规划与合规要求（当前代码**未实现**）

> 本附录写的是「门店真实经营需要、系统目前没有」的部分，与正文的现状描述严格分开。正文回答「现在是什么样」，本附录回答「按合规与实务应做成什么样」。可执行细节（建表语句、接口契约、验收用例）见 `docs/业务补齐方案.md`。
>
> **更新提示（2026-11-06）**：员工端小程序已落地岗位鉴权、VET 资质与在岗判定、交接签字、异常通知渠道与时间、按岗位核销、巡视幂等等控制（见§十一），因此 A.2 / A.3 里「现状一条都没有」「`position` 只是标签」的表述**现在仅适用于 Web 端与客户端**。Web 端权限矩阵、`@RequireCapability` 拦截器、`store_license` / `data_export_log` 等仍未实现。

### A.1 合规为什么是硬门槛，而不是加分项

寄养期间，门店在法律上就是动物的**管理人**。以下四条规定决定了"必须有记录"：

| 依据 | 要点 | 对应系统要求 |
| --- | --- | --- |
| 民法典第 1245 条 | 饲养的动物致害，**饲养人或者管理人**承担侵权责任 | 入离店交接、每日巡视、异常处置记录——这是"已尽管理义务"的唯一证据 |
| 民法典第 1246 条 | 违反管理规定、未对动物采取安全措施致害，承担责任 | 牵引、猫犬分区、烈性犬拒收必须留痕，否则无法证明"采取了措施" |
| 民法典第 1247 条 | 禁止饲养的烈性犬等危险动物致害，承担责任（**无免责事由**） | 下单与入店都要能识别并拦截；协议免责条款对此条无效 |
| 民法典第 1249 条 | 遗弃、逃逸的动物在逃逸期间致害，由原饲养人**或者管理人**承担 | 走失必须留时刻与处置记录 |

防疫与个人信息另有硬要求：

| 依据 | 要点 | 对应系统要求 |
| --- | --- | --- |
| 动物防疫法第 7、24、31 条 | 做好免疫、消毒、检测、隔离；防疫条件含执业兽医与隔离消毒、台账、日常巡查制度；发现染疫或疑似染疫应立即报告并隔离 | 免疫证明核验、消毒台账、执业兽医资质、疑似传染病强制隔离与报告字段 |
| 动物防疫法第 25 条 | 开办动物饲养场和隔离场所应取得动物防疫条件合格证 | 门店证照留档与到期提醒（是否需办按当地认定，系统不替他下结论） |
| 个人信息保护法第 6、13、17、19 条 | 最小必要、合同必需可不经单独同意但须告知、告知保存期限、保存期限取最短必要 | 不采身份证与人脸；手机号打码；档案保存 2 年；导出留痕 |

### A.2 六条硬控制（现状一条都没有）

1. 无有效免疫证明不得寄养——**下单与入店两处都校验**，只拦一处等于没拦；
2. 烈性犬、术后 7 天内、发情期、体外寄生虫——拒收并留证；
3. 猫犬不混区，单宠单笼；
4. 入店交接四项齐（称重、照片、物品清单、客户签字），缺一项不许入店；
5. 异常必须登记通知渠道与时间才可闭环；
6. 疑似传染病——强制置「隔离」、报告对象与时间必填、一键导出同区宠物联系人。

配套两张表（`store_license` 门店证照、`data_export_log` 导出留痕）与四个规则键（档案留存 730 天、异常 2 小时内通知、导出必填用途、证照提前 60 天提醒）。举证接口为 `GET /api/orders/{id}/archive`：一份订单导出七件套（免疫证明、交接单、三班巡视、异常与通知、送医授权、消毒记录、账单明细）。

### A.3 岗位与资质（现状 `staff.position` 只是标签）

核实结论：`position` 目前只在 `StaffService` 存取、`AuthService` 回填 VO、`SysUserVO` 带回前端，**没有任何一处用它判断权限**。需要细分，但分的是岗位而非系统角色：

- 六个岗位代码（存代码不存中文）：`OWNER` 店长／管理员（系统角色 `sys_admin` 的落点，不新增角色）、`FRONT` 前台、`CARE` 护理员、`GROOM` 美容师、`DRIVER` 外勤接送、`VET` 兽医；**宠物医生全职在岗**（本项目已定），系统内须有一个持有效执业兽医证的 `VET` 账号并纳入 `staff_shift`（排班功能模块暂不实现：仅建表，店长手工录当日 VET 班次支撑在岗判定）；
- 三个能力组由岗位派生：A 经营配置、B 接待结算、C 照护记录；
- 各岗位的工作内容与 Web / 员工端页面权限矩阵（谁写、谁只读、谁不能看）见《业务补齐方案》11.12；
- 诊疗边界：全职兽医只做健康评估、处置复核、送医判断；诊断、处方、注射、手术属动物诊疗活动，须由持《动物诊疗许可证》的机构承接（动物防疫法第 62 条、动物诊疗机构管理办法第 5 条），系统只存转诊单与外部处方编号；
- 五个资质判定点：填观察记录须 CARE/VET；处置类记录（异常/处理措施）须执业兽医复核，入离店健康评估须执业兽医签署；送医授权须 `cert_type='执业兽医'` 且证在有效期（紧急可由店长先记、24 小时内补签）；交接签字须 FRONT/CARE 并存 `signer_position` 快照；增值服务核销按岗位分工。

### A.4 补齐规模（可对照进度）

- 新增 **16 张表**：`foster_room`、`foster_room_booking`、`foster_handover`、`foster_care_log`、`foster_incident`、`foster_disinfection_log`、`store_env_log`、`pet_cert`、`foster_bill_item`、`pet_reject`、`staff_cert`、`staff_shift`、`biz_rule`、`store_license`、`data_export_log`、`service_item`（增值服务价目表，替代前端硬编码 30/20/40）；
- `foster_order` 等表共 **12 处 ALTER**（`foster_order` 增 7 列、`staff.positions`、`pet_health_record` 增 4 列：记录人岗位快照、复核兽医、复核时间、外部处方编号）；
- **22 条验收用例**（U1–U22，Given/When/Then，可直接转 E2E）；
- **三端分工**：顾客小程序（下单/支付/评价）+ 员工端手机（今日待办、入离店交接、巡视拍照、异常上报、服务核销）+ 管理端 Web（收银、档案、班次录入、报表；排班模块暂不实现）；员工端只做现场动作，收银与导出仍留 Web（见方案 11.11）；
- **同一账号多端数据同步**：同一员工账号在 Web 与员工端登录，岗位/能力组/待办/交接/核销/账单来自同一份数据，一端写入另一端立即可见（见 PRD 3.7 与方案 11.14）；
- **排班功能模块暂不实现**：排班页面/轮班规则/待办驱动不做，仅建 `staff_shift` 表＋店长手工录当日班次支撑 U20/U21 在岗判定，U12 随排班模块一并暂缓；
- **五个批次**：批零（合规，先做）→ 批一（钱）→ 批二（房）→ 批三（责任链与人员）→ 批四（效率）。

### A.5 计费口径要统一为「按天」（照护日）

协议、首页、结算页现在按「晚」（`晚数 = 离店 − 入住`，同日按 1），后端 `calcTotalFee` 按「天」（`离店 − 入住 + 1`），同一订单两套金额。**已定口径为按天**：`计费日数 = max(1, 离店 − 入住 + 1)`，入住日与离店日均计 1 日——门店卖的是代照护，白天喂食、遛放、清洁都在发生。落地只需改前端 `calcDays`（加 `+1`）与协议文案整段重写，后端、种子数据、历史订单金额都不动。四处（页面预估、订单、支付成功页、导出）必须一致，且结算页要显示「共 N 个照护日（含离店当日）」，否则短住客户会认为多收。
