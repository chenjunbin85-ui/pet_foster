# 毛球旅馆 · 业务流程核查报告

> 核查对象：`docs/项目文档.md` 所描述的业务流程，对照 `C:\Users\chen\Desktop\毕业设计\pet-foster` 当前工作区代码，以及 127.0.0.1:8090 上运行中的后端。
> 核查时间：2026-11-05
> 核查方法：读源码定位规则 + 调用接口实测。登录使用三个演示账号；只调用只读接口；注册接口仅用非法参数探测（未写入数据）。
> 核查范围：注册 → 建档 → 预订计费 → 支付 → 入店照护 → 离店评价 → 取消退款 → 后台权限 → 统计导出。
> 未纳入：技术选型与组件版本、设计 token、前端视觉还原度。

---

## 一、结论摘要

文档第七节写的是一条**完整闭环**：下单（未支付）→ 15 分钟内支付 → 超时自动关单 → 入店建档 → 照护留痕 → 离店结算 → 评价。代码实际跑的是另一条更短的链路，并且金额侧存在三套口径。

最需要先处理的六个问题：

1. **注册链路断了**：`POST /api/mp/auth/register` 未在安全配置放行，实测返回 **401**，新客户无法自助注册。
2. **支付环节被架空**：下单即置「已支付（微信）」，不写 `expires_at`，结算页直接跳「支付成功」；支付页、倒计时、超时关单全部空转。
3. **一单三种金额**：结算页展示金额 ≠ 订单总金额 ≠ 实际计费规则；**跨天订单一律比页面多收 1 天房费**。
4. **增值服务与优惠券只停留在展示层**：前端计入总价并传参，后端不计费、不核销。
5. **照护动态没有数据来源**：`care_record` 只有读接口，全仓库没有任何写入方，客户照护面板永远是空的。
6. **角色权限与业务分工相反**：管理员看不到客户/宠物档案（403），员工看不到经营统计（403）；导出权限两个角色互补互斥。

另有一条不属于流程缺陷、却影响全部结论的：**核查所依据的 8090 实例是 17:15 的旧构建，之后源码又改过**（库里甚至没有 `staff` 表），详见 B17 / 3.17。B1–B16 的接口结论在新构建重启并迁移库后需复核。

## 三、逐条说明

### 3.1 B1 注册接口被拦截（高）

- **实际**：安全配置只放行 `/api/auth/login`、`/api/mp/auth/login`、`/health`、Swagger，其余 `anyRequest().authenticated()`。`register` 未在白名单，实测 `POST /api/mp/auth/register`（无 token）返回 **401**。
- **业务后果**：新客户只能看登录页，「注册→登录→下单」的完整演示链路走不通；文档 7.1 描述的注册流程实际不可达。
- **建议**：把 `/api/mp/auth/register` 加入放行名单；注册仍保留手机号占用校验与 BCrypt。改完后用真实新号跑一遍注册→下单。

### 3.2 B2 支付环节被架空（高）

- **实际**：
  - `MpOrderService.create` 直接置 `payment_status=已支付`、`payment_method=微信`、`payment_time=now`，**不设置 `expires_at`**；注释写明「下单即完成支付（演示）」。
  - 小程序结算成功后 `wx.redirectTo` **直接进入支付成功页**，不再经过支付页。
  - `orders.js` 注释：「订单创建即已支付，不再区分支付态」。
  - `pay()` 只对「未支付」订单有效；`OrderExpireTask` 只扫「待入店 + 未支付 + expires_at 已过期」，而这类订单已不存在，定时任务空转；`PAY_TIMEOUT_MINUTES=15` 常量未被使用。
  - Web 端建单同样「创建即完成收款」，支付方式固定微信；前端虽有收款弹窗，但已付款订单不会出现入口。
- **业务后果**：没有「待支付」订单，也就没有放弃支付、支付失败、超时关单这些真实业务分支；线下现金收款无法如实记录（收款方式被写死成微信）；支付页与倒计时成了死页面。
- **建议**（二选一，必须统一）：
  - **A. 恢复支付环节**：下单只置「未支付」并写 15 分钟 `expires_at`，支付成功后置已支付；保留 `OrderExpireTask`。这条更贴近门店真实流程，也最能体现业务流程完整性。
  - **B. 明确简化**：承认「下单即支付」，删除支付页/倒计时/超时关单，并把支付方式交给门店选择（现金/微信/支付宝）。
  - 无论哪种，都要保证「订单状态」与「支付状态」在列表、详情、导出、统计里口径一致。

### 3.3 B3 计费口径前后端差一天（高）

- **实际**：
  - 前端 `utils/util.calcDays`：晚数 = 离店 − 入住（同日按 1），结算页房费 = 晚数 × 单价。
  - 后端 `FosterOrderService.calcTotalFee`：天数 = 离店 − 入住 **+ 1**，订单总额 = 单价 × 天数。
  - 实测口径差：舒适间 80 元/晚，`2026-10-25 → 2026-11-05` 前端算 **11 晚 = 880 元**，后端算 **12 天 = 960 元**；种子订单 `FO20261025002` 的 `total_fee` 正是 **960**。
  - 结论：**所有跨天订单，后端都比页面多收 1 天房费**；同日订单两边一致。
- **业务后果**：结算页看到 880，跳到支付成功页显示 960，订单、导出、统计全部按 960。用户当场能看到差额；协议文本还写着「按晚计费」，属于承诺与实收不一致，是最容易被投诉的一条。
- **建议（已定：按天）**：统一为**照护日**口径，`计费日数 = max(1, 离店 − 入住 + 1)`，入住日与离店日均计 1 日。理由是门店卖的是代照护——喂食、遛放、清洁、观察都在白天发生，按过夜的「晚」收费说不通。后端 `calcTotalFee` 现在就是这个算法，种子订单 960 元与历史订单金额都不用动，只需前端 `calcDays` 加 `+1`、协议文案整段重写。代价是短住报价比「按晚」高一档（今天入、明天走算 2 日），因此结算页必须显示「共 N 个照护日（含离店当日）」。若门店日后想回到按晚，把 `biz_rule.billing.checkout_day_charge` 置 0 即可，不改代码。

### 3.4 B4 增值服务只展示不计费（高）

- **实际**：首页有洗护美容 30、每日遛宠 20、上门接送 40 三项，结算页计入总价并展示；提交时**只把服务名拼进 `remark` 文本**（`增值服务：洗护美容`），`MpOrderCreateDTO` 没有增值服务字段，后端 `totalFee` 只算房费。
- **业务后果**：客户选了「洗护+接送」，展示价 +70，订单金额不变；门店也没有对应的服务待办，买了不一定做、做了不一定记账。
- **建议**：把增值服务落成订单明细（独立表或订单项 JSON），下单时计价、生成服务待办，离店时逐项核销；小程序详情与后台服务记录共用同一份数据。

### 3.5 B5 优惠券不抵扣、不核销（高）

- **实际**：结算页显示「-20」并把 `couponId` 传给后端；`MpOrderCreateDTO` 也有 `couponId` 字段，但 `MpOrderService.create` 完全没使用它。全仓库 `CouponMapper` 只用于「我的优惠券」列表查询，没有任何状态变更。实测客户 1 有一张「新用户首单立减 20」，状态仍是 `UNUSED`。
- **业务后果**：用户以为已优惠，实付没减；同一张券可以无限次「使用」；券的满减门槛、有效期、归属都没有校验。
- **建议**：下单时校验归属/状态/门槛/有效期 → 计算抵扣 → 置 `USED` 并回写 `order_id`；下单失败要回滚券状态。

### 3.6 B6 照护动态没有写入方（高）

- **实际**：`care_record` 全仓库只有 `MpCareController` 的 `GET /api/mp/orders/{orderId}/care` 一个读取点，没有 insert/update；员工端写的是 `foster_service_record`（喂食/遛弯/洗澡）和 `pet_health_record`，两条链路没有打通。
- **业务后果**：小程序订单详情里的「照护动态」永远是空列表；文档 7.3「客户实时看到这些照护动态」不成立。另外该读取接口**不校验订单归属**，A 客户可以读 B 客户订单的照护记录。
- **建议**：员工端「每日照护」直接写 `care_record`（或由 service/health 记录聚合投影出来），并在读取时校验 `order_id` 属于当前客户。

### 3.7 B7 入店/离店不与健康档案、结算联动（中）

- **实际**：`checkIn` 只把状态从「待入店」改「寄养中」，`checkOut` 只改「已完成」；都不生成健康记录，也不校验入离店日期。
- **业务后果**：文档说的「入店写入首条健康记录」「离店补离店记录」实际要员工手工另录（健康记录里的「关联订单」还是选填）；提前离店不退款、超期离店不补费，计费天数与实际住店天数脱钩。
- **建议**：入店动作强制生成一条入店健康记录（体温/精神/食欲/皮肤）；离店生成离店记录，并按实际住店天数做补退；入离店日期做软校验（提前/超期要提示并走调整流程）。

### 3.8 B8 评价门槛与归属校验缺失（中）

- **实际**：`MpReviewController.submit` 只校验订单归属与「一单一评」，**不校验订单是否已完成**；`GET` 接口不校验归属。小程序只在「已完成」订单展示评价入口，但接口层没拦。
- **业务后果**：待入店订单也能提交评价；任意客户可读他人订单评价。
- **建议**：提交前校验 `status=已完成` 且归属当前客户；读取同样校验归属。

### 3.9 B9 取消与退款两端不一致（中）

- **实际**：
  - 小程序 `cancel`：待入店/寄养中可取消，已支付则置「已退款」。
  - Web `cancel`：只把状态改「已取消」，**不回写退款状态**；但 Web 建单时已置「已支付」。
  - 协议文本承诺「入住前 24 小时免费取消，逾期收 1 晚手续费」，代码里没有任何时间/手续费判断。
  - 小程序列表只对「待入店」给取消入口，后端却允许「寄养中」取消。
- **业务后果**：同一个订单在小程序和后台看到的退款状态不一致；客服无法解释扣费；寄养中退订在线下没有入口。
- **建议**：把「可取消时间窗 + 手续费规则」写成显式规则函数，两端共用；取消时同步写退款状态与退款金额；前端按后端返回的可取消状态渲染按钮。

### 3.10 B10 没有房态，超订无拦截（高）

- **实际**：`foster_price` 只是价格档位（标准间/舒适间/豪华间），没有房间数量、床位、占用区间；下单不查任何库存，同房型同日期可以无限下。
- **业务后果**：宠物旅馆的核心资源是「房」，没有房态就会出现同一间房被多个订单占用，到店无房；也没有「待清洁/维修/停用」这些真实房态。
- **建议**：房型加 `capacity`，下单做日期区间占用校验（或做房态日历：空闲/已预订/在住/待清洁）；入店占房、离店释放；节假日单独设加价与库存。

### 3.11 B11 角色权限与业务分工相反（高）

接口实测矩阵（演示账号 admin / staff01）：

| 接口 | 管理员 admin | 工作人员 staff |
| --- | --- | --- |
| `GET /api/customers` | **403** | 200 |
| `GET /api/pets` | **403** | 200 |
| `GET /api/health-records` | **403** | 200 |
| `GET /api/service-records` | **403** | 200 |
| `GET /api/orders` | 200（只读；入离店/取消/收款为 STAFF） | 200 |
| `GET /api/prices`（CRUD） | 200 | 403 |
| `GET /api/prices/options` | 200 | 200 |
| `GET /api/stats/dashboard` | 200 | **403** |

- **业务后果**：文档写「管理员：客户/订单全局管理」，实际管理员打不开客户与宠物档案，也导不出客户/宠物；员工看不到经营报表但不能导出订单。管理员登录默认进统计页，侧边栏也没有客户/宠物入口，想看客户资料只能靠员工账号。
- **建议**：先定业务职责（谁建档、谁看报表、谁导出），再让权限矩阵对齐；如果管理员需要「全局查看」，至少给客户/宠物只读权限，导出权限也按「谁能看谁导出」对齐。

### 3.12 B12 统计口径两个角色不一样（中）

- **实际**：管理员走 `GET /api/stats/dashboard`，`countMonthlyOrders` 按 `create_time` 统计、`sumMonthlyRevenue` 统计 `total_fee`（`status != 已取消`）。员工首页改为拉 `orderPage(1, 1000)` 全量订单，在前端按 `createdAt` 前缀过滤本月；金额走 `monthly-revenue`（同一条 SQL）。
- **业务后果**：两个角色看到的「本月订单」可能不同；营收口径是「订单总额」而不是「实收」（`paid_amount`），已退款但状态未变「已取消」的订单仍会被计入。
- **建议**：统一成一个统计接口，明确「订单数」按创建时间、「营收」按实收（排除已退款），并给员工首页做轻量只读视图，避免拉 1000 条订单。

### 3.13 B13 状态文案与时间线错位（中）

- **实际**：
  - 小程序列表把「待入店」显示为「待入住」、「已取消」显示为「已关闭」；后台、导出、接口仍是原值，形成两套叫法。
  - `orderDetail.buildTimeline` 在「待入店 + 已支付」时把当前节点置为第 2 步「宠物已送达」，但宠物还没到店。
- **业务后果**：客服口径混乱（用户说「我的待入住订单」，后台查「待入店」）；用户看到「已送达」会以为宠物已经交接。
- **建议**：状态只保留 4 个枚举值，展示别名集中在一个词典；时间线由真实事件时间驱动（入店时间、离店时间、支付时间），不要用状态推断「已送达」。

### 3.14 B14 订单号并发撞号风险（中）

- **实际**：`generateOrderNo` = `FO + yyyyMMdd + 当日订单前缀物理计数 + 1`，无锁、无冲突重试。
- **业务后果**：并发下单可能生成同一订单号，触发唯一键冲突，表现就是「下单失败」。
- **建议**：用序号表或 Redis 自增发号，或捕获唯一键冲突后重试；订单号生成与业务写库放同一事务边界内。

### 3.15 B15 门店写死、演示数据不一致（低）

- **实际**：小程序下单 `storeId` 取 `stores[0]`，缺省 1；后端不校验门店是否存在/是否营业。门店表只有一条「毛球旅馆·西湖总店（杭州）」，而种子客户地址在泉州。
- **业务后果**：多门店场景不成立；演示时门店信息与客户地区对不上，答辩容易被问。
- **建议**：结算页让客户选门店并校验营业时间；订单落门店外键；演示数据统一到一个城市。

### 3.16 B16 疫苗判定前后端不一致（中）

- **实际**：后端 `VaccineJson.isVaccinated` 对历史中文文本（如「狂犬疫苗已接种」）**视为已免疫**；小程序 `utils/util.vaccineDetails` 只认字符串「已接种」或 JSON `status=已接种`，历史文本被判「未免疫」。
- **业务后果**：实测客户 1 的「豆豆」(`vaccine="狂犬疫苗已接种"`) 在小程序被拦「未接种疫苗暂不可预约」，无法下单；而后台仍可为它建单。同一只狗两个入口两种结论。
- **建议**：统一解析规则（后端与小程序共用一套判定）；或把历史文本一次性迁移成 JSON 结构，`petEdit` 保存时强制写 JSON。

### 3.17 B17 代码、库、运行实例三者不一致（高）

- **实际**：
  - **库**：`pet_foster` 里只有 `sys_user(user_id, username, password, real_name, role, status, create_time, remark)`，**没有 `staff`、没有 `sys_admin`，也没有 `position` 列**；两条数据为 `admin`(role=admin)、`staff01`(role=staff，张护理)。
  - **接口**：`GET /api/users` 返回 `id/username/name/role/status/remark/createdAt`，**没有 position 字段**。
  - **源码**：`Staff.java` 是 `@TableName("staff")` 且含 `position`；`schema.sql` 建的是 `sys_admin` + `staff`。
  - **时间**：8090 进程（PID 39276）创建于 **17:15:32**，跑的是 `target/classes`；`Staff.java`（18:12:33）与 `schema.sql`（18:12:25）都在其后修改。
- **业务后果**：
  1. 文档 3.1 写的 `staff` 表在当前库里不存在，「岗位」在线上没有任何落点，岗位细分只能从零加；
  2. **本报告 B1–B16 的接口实测是针对 17:15 旧构建做的**，此后的源码改动（`staff` 回归、岗位字段）尚未运行，重启并迁移库后必须按 3.11 矩阵复核一遍；
  3. 演示账号能登录**不能**证明表结构一致——登录走的是旧构建读 `sys_user`。
- **建议**：先写迁移脚本（把 `sys_user` 拆成 `sys_admin` / `staff`，或统一实体映射到一张表）→ 重建库 → 重启新构建 → 重跑 B1–B16 的接口项并刷新结论。此后每次核查先记一条「进程启动时间 vs 源码修改时间」，避免拿旧构建的结论套新代码。

### 3.18 B18 员工端缺位：拍照记录只能靠 Web 事后补录（中）

- **实际**：
  - 小程序 `app.json` 共 11 个页面——`login`、`register`、`index`、`checkout`、`pay`、`payResult`、`orders`、`orderDetail`、`pets`、`petEdit`、`mine`，**全部面向客户，没有员工页面、也没有员工登录入口**。
  - `MpCareController` 类上 `@PreAuthorize("hasRole('CUSTOMER')")`，唯一方法是 `GET /api/mp/orders/{orderId}/care`，**只读**。
  - `care_record` 有 `image_url`（单张 `varchar(255)`），但**全仓库没有写入方**（与 B6 同源）；后端也**没有任何上传能力**（全 `src/main` 搜不到 `MultipartFile` / OSS 相关代码）。
- **业务后果**：照护照片只能等员工回工位用 Web 补录——「每天三次巡视、每次留痕」在犬舍现场无法完成，照片失去「那一刻在现场」的意义；顾客端照护面板也永远为空。主流寄养的卖点恰恰是"每天看照片"，这一条直接断了。
- **建议（不整体迁移，按三端分工，见方案 11.11）**：
  - 顾客小程序不变（下单、支付、订单、宠物、照护只读、评价）；
  - 新增员工端（同一小程序按角色分流）：今日待办、入店/离店交接、巡视打卡拍照、异常上报、服务核销；
  - 新增两个后端能力：图片上传接口、照护写入接口（写 `foster_care_log`，投影 `care_record`）；
  - 收银、对账、导出、价格与规则配置仍留 Web——这些在手机上做不了。
- **验收**：方案 U22（员工手机提交 3 张照片 + 异常 → `foster_care_log` 一条、顾客端可见、重复提交不新增）。

## 九、对照现实业务的补齐清单

第七节是粗表，本节按真实门店的操作流程与行业规范细化，并落到"要补哪些数据、要补哪些规则、怎么验收"。

> **依据与效力说明**：`T/CVMA` 的寄养卫生安全规范是行业协会团体标准（草案，非强制），管的是**卫生与记录**；北京公示的动物寄养防疫规定是地方性规定（对当地有约束力），管的是**准入与防疫**；港台与海外门店的住宿条款代表**通行商务惯例**，管的是**钱与责任**。这三类内容，现在的系统一类都没有。
>
> 主要依据：
> - 宠物寄养卫生安全管理技术规范（团体标准草案）：接收时基本检查、查验免疫驱虫资料、掌握病史过敏史；每日至少早中晚三次巡视并记录精神/运动/被毛/饮食/排泄；异常事件记录、消毒记录、记录保存不少于两年、可追溯接触史
> - 北京市动物寄养活动防疫管理规定：须有兽医专业技术人员、消毒与废物处理设施、隔离饲养与疑似染疫隔离区；建立进场检查制度（健康检查+免疫查验+入场登记）；日常健康检查并记录，疑似传染病隔离
> - 香港渔护署动物寄养所牌照条件：备存有效防疫注射证明、寄养登记册、每日至少喂食一次、每日清排泄、不混养、病宠隔离
> - 门店住宿条款（台/澳/英样本）：定金比例、阶梯退费、超时费、逾期未接处置、送医授权与费用由主人承担

### 9.1 现实门店的八段链路与硬控制点

| 阶段 | 现实必须做到（不做到就出事） | 系统现状 |
| --- | --- | --- |

| 2 入住前资质审核 | 查验疫苗在保护期内、驱虫记录；体表与精神状态初检；登记病史、过敏、用药；对幼犬、老年基础病、术后 7 天内、传染病、体外寄生虫、发情期明确拒收 | 只有 `vaccine` 一个字段且前后端判定不一致（B16）；无驱虫、无附件、无拒收规则 |
| 3 入店交接 | 当面体表检查、称重、拍照；随身物品清点签字；紧急联系人、送医授权、指定医院确认；签寄养协议 | 点一下「确认入店」只改状态（B7），无交接单、无照片、无签字、无授权 |
| 4 在住照护 | 每日至少早中晚三次巡视并记录精神、运动、被毛、饮食、排泄；定时喂食换水清排泄；犬只定时外遛；猫狗分区、单宠单笼不混养；疑似染疫单独隔离 | 客户侧 `care_record` 无写入方（B6）；员工只能手填健康/服务记录，无班次频次要求、无房位分区 |
| 5 异常处置 | 发现异常→隔离→通知主人→按授权送医→费用由主人承担→记异常事件（时间、情况、处置） | 健康记录有「异常/处理措施」字段，但没有处置流程、没有通知、没有授权与费用记录 |

| 7 售后 | 评价、回访、复购；隐瞒传染病者进黑名单 | 评价可提交但不校验状态（B8）；无回访、无黑名单 |
| 8 后台与合规 | 房态日历；排班与兽医资质；消毒记录；温湿度记录；寄养登记册；记录保存两年以上；能追溯接触史 | 只有订单/客户/宠物/记录四类表，无消毒、温湿度、登记册、资质、追溯能力 |

### 9.4 合规留痕（现实最不能省、答辩最容易被问的一段）

- **巡视记录**：每日至少早中晚三次，内容含精神、运动、被毛、饮食、排泄；异常另设栏位并启动处置流程。
- **消毒记录**：时间、区域、药剂、浓度、操作人；发生体液/排泄物污染立即清洁消毒；退房后彻底消毒再放下一只。
- **环境记录**：温湿度每日上、下午各一次；有害生物每月检查。
- **异常事件记录**：时间、情况简介、处置结果；记录保存不少于两年。
- **可追溯**：能回答「某只宠物在住期间接触过哪些宠物、用过哪个笼位」，出传染病才能拦住同批。
- **隔离与分区**：疑似染疫单独隔离；猫狗分区；单宠单笼，笼位排列避免相互对视。

### 9.5 优先级与验收

**P0-A 合规（先做，不可协商）**

按「合规第一」重排：这一组是出事时能自证的最低配置，且不依赖计价与房态，可以最先落。

1. 免疫证明核验——**下单与入店两处都拦**，附审核状态与到期日
2. 猫犬分区、单宠单笼、疑似染疫立即隔离
3. 入离店交接单（称重 + 照片 + 物品清单 + 客户签字）——出事时的第一份证据
4. 异常通知留痕（渠道 + 时间）与疑似传染病报告字段（报告对象、报告时间）
5. 消毒台账、温湿度台账
6. 门店证照留档（营业执照、动物防疫条件合格证等）与到期提醒
7. 导出留痕、手机号脱敏、寄养档案保存 2 年（到期脱敏归档）

**P0-B 钱（与合规同批）**

8. 计费口径统一 + 增值服务与优惠券入账 + 账单明细（价目与账单不一致，本身就是合规问题）
9. 定金与阶梯退费

**P1（把合规变成可持续运营）**

10. 房态（房间 + 占用 + 清洁/隔离状态）
11. 每日巡视写入（三班待办 + 客户可见）
12. 排班与资质判定（谁有资格签字）

**P2（经营效率）**

13. 拒收复核、评价运营、多门店、押金对账、商品/日托/上门喂养

> 法条依据：民法典第 1245/1246/1247/1249 条、个人信息保护法第 6/13/17/19 条、动物防疫法第 7/24/25/31 条。系统落点、六条硬控制、验收 U14–U18 见 `docs/业务补齐方案.md` 第十节。

**验收标准**
- 任一订单能导出一份完整寄养档案：免疫与驱虫证明、交接单、每日巡视、异常事件、消毒记录、账单明细，且金额在结算页、订单、支付成功页、导出四处一致。
- 出传染病时，能在 1 分钟内列出同期间同区域住过的宠物及主人联系方式。
- 「提前离店、超时未接、隐瞒传染病」三种情形，系统都能给出明确处置动作，而不是靠员工记忆。

### 9.6 与 B1–B16 的关系

B1–B16 是「现有功能跑错了」，9.1–9.5 是「该有的功能没有」。修 B 系列不改系统定位；补 9 系列才让它从「能下单的页面」变成「能受托的旅馆」。动工顺序建议：先把 B3/B4/B5（钱）与 P0-4 合并成一处改（同一段计价代码），再做房态与交接单——这两项一动，订单、房态、账单、巡视记录四条数据就都立起来了。

### 9.7 工作人员要不要细分

**结论：要分岗位，但不要再多开系统角色。**

现状（已核实）：`staff.position` 只是标签。服务端只有 `StaffService` 存取、`AuthService` 回填到登录信息、`SysUserVO` 带回前端这几处；没有任何一处按岗位判权限，Web 端也没有岗位相关逻辑（搜到的 `position` 全是 UI 库的 `Positioner`）。所有员工共用一个 `STAFF` 角色——前台、护理员、美容师在系统里完全等价，连导出权限都一样。

现实里必须分的三个理由：

1. **资质要求**：规范要求寄养机构「有兽医专业技术人员」，日常健康检查、疑似染疫隔离由专业人员做。现在任何员工都能填体温、判异常。
2. **责任追到人**：每日三次巡视要能回答「今天该谁巡视这只狗、漏了没」。现在没有排班、没有岗位，只能靠记忆。
3. **权限最小化**：美容师、外勤不该有取消订单、改价位、导出的权限，而现在都有。

建议分三层，不要按岗位铺权限矩阵：

| 层 | 内容 | 用途 |
| --- | --- | --- |
| 岗位 | 店长、前台接待、护理员、美容师、外勤接送、兽医（外协可标注） | 派工、排班、记录署名、增值服务核销 |
| 能力组（3 组） | A 经营配置、B 接待与结算、C 照护与记录 | 判权限，只判 3 组，不做 6×N 矩阵 |
| 资质 | 兽医执业/护理培训、疫苗核验、送医决定 | 决定「能不能签字」 |

岗位到能力的映射（建议）：

| 岗位 | 能力组 | 说明 |
| --- | --- | --- |
| 店长／管理员（admin 落点） | A + B + C | 以 A 为主，兼任时可签字；系统角色 `sys_admin`（管理员）落点为店长，不新增角色 |
| 前台接待 | B | 客户建档、收银、入店登记；**不做健康判定** |
| 护理员 | C | 喂食、遛放、巡视、填健康记录 |
| 美容师 | C（限增值服务） | 只做洗护类核销，不改订单、不判健康 |
| 外勤接送 | 仅接送任务 | 不接触档案与账目 |
| 兽医（**全职在岗**） | C + 判定权 | 入离店健康评估、判异常、定隔离、送医授权、处置复核（不得开展诊疗，诊断处方转持证机构） |

最小改动只有两个概念：

1. **岗位改多值**：`staff.positions`（JSON 数组或逗号串），一人多岗在小门店是常态；前端下拉改多选。
2. **加 `shift` 与 `cert`**：`shift`（日期、班次、staff、岗位）派生「当日主责护理员」；`cert`（兽医/护理资质）决定签字权。

四个判定点，够用了：

| 动作 | 谁能做 |
| --- | --- |
| 填健康记录、判异常 | 护理员、兽医 |
| 决定隔离/送医、签送医授权 | 仅持证兽医（紧急可由店长先记，24 小时内兽医补签） |
| 入店/离店交接签字 | 前台、护理员（谁接谁签） |
| 增值服务核销 | 洗护→美容师；接送→外勤；遛宠→护理员 |

不建议的做法：给 6 个岗位各开一个系统角色再叠到现有接口上（权限矩阵会失控）；给美容师、外勤订单取消权；让前台替兽医决定「要不要送医」。

验收：任一健康异常、交接单、送医授权，都能回答「谁签的、什么资质」；能回答「今天谁负责这只狗」（排班模块暂不实现，靠店长手工录当日班次支撑，见方案 11.5）。

### 9.8 现实门店运营工具对照（检索于 2026-11-05，回答"员工端＋Web 是不是现实"）

| 现实形态 | 代表产品 | 与我们的方案对照 |
| --- | --- | --- |
| 前台、美容师与店长围绕同一张服务单协同，宠主在微信小程序看服务进度；手机/平板/电脑即可开店 | 旺星管家（国内 SaaS，单店首年 688 元） | 形态一致：员工现场拍照、顾客端可见；旺星无需专用收银机，我们把收银放 Web 也成立 |
| 老板/店长用**管理端小程序**做排班、收银、业绩 | 贝灵顿（国内） | 店长管理端做成小程序是国内常见形态；我们选「同一个小程序按角色分流」，形态近似 |
| 主人点链接要照片/视频，店员收到通知后拍照上传 | Petzio（海外 boarding） | 解决「主人反复打电话要照片」；我们改为巡视即拍照入库、顾客端只读，主动推送 |
| 一张照片＋几句备注，手机一分钟发出，主人同线程回复 | Goodstay（海外 kennel） | 对应我们的「每日照护更新」；我们不建聊天线程，只留痕 |
| 店员扫订单二维码进安检页，按指引拍正脸/侧身/背部/腹部/口腔/肛门 6 张＋1 段视频；异常强制标注部位再拍；主人手机实时收入店确认 | 蓝橙·宠物代养系统方案 | 与 11.11「入店交接拍照、异常强制标注、顾客端可见」**直接对标**，证明我们的流程设计是现实做法 |
| 护理员佩戴工牌/手持设备 NFC 打卡，强制上传带时间地点操作人水印的照片 | 蓝橙·宠物监护方案 | 我们用水印（时间＋工号＋班次）替代 NFC 硬件，防漏检/假检的意图一致 |
| 扫码枪＋小票机＋钱箱收银联动；寄养监控摄像头，顾客小程序看直播 | 蜗牛小店 | **两处现实有、我们明确不做**：收银硬件联动、监控直播（列 P2+，见未决问题） |
| 柜台平板 check-in，2 张图＋1 段视频拼成当日更新发给主人 | Toca（海外，巴西） | 我们用手机替代平板，本质相同 |

**结论（实话实说）**：「店员手机拍照回传＋主人端实时可见＋前后台围绕同一单协同」是国内外寄养门店的主流刚需，不是我们发明的形态；但具体形态多样（柜台平板、管理端小程序、独立 APP、微信直发）。我们的「员工端＝同一个小程序按角色分流」是为毕设约束（不新增独立端）取的最省实现，形态上接近旺星管家/贝灵顿；与蓝橙方案的入店拍照、异常强制标注流程一致。两处现实有而本方案不做：收银硬件联动、监控摄像头直播——前者不涉及业务流程，后者需要流媒体能力，均超出「只看业务流程」的范围。
