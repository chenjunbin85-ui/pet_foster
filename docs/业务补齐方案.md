## 一、先把口径定死（否则后面全白做）

三处金额不一致的根因是「按天」和「按晚」并存。**这里定为按天**：门店卖的不是一张床，是「代照护」—— 客户白天在上班，喂食、遛放、清洁、观察全发生在白天，所以按**照护日**收费，而不是只按过夜的晚数收费。



| 口径项                | 定义                                               | 说明                          |
| ------------------ | ------------------------------------------------ | --------------------------- |
| 计费日数 `charge_days` | `charge_days = max(1, DATEDIFF(离店日, 入住日) + 1)`   | 入住日与离店日**都算 1 日**；同日入离算 1 日 |
| 应收房费               | `应收 = 单价 × 计费日数 + 节假日加价`                         | 单价取价位快照 `price_per_day`     |
| 应收总额               | `total_fee = 房费 + 增值服务 + 医疗 + 超时费 + 赔偿 − 优惠`     | 明细落 `foster_bill_item`      |
| 实收                 | `paid_amount = 定金 + 尾款 − 退款`                     | 统计、导出、对账统一用实收               |
| 房间占用区间             | 半开区间 `[occupy_start, occupy_end)`，退房当天可入住下一只     | 占房按「夜」算，与计费按「日」是两回事，互不影响    |
| 离店日开关              | `billing.checkout_day_charge`：`1` 计费（默认）/ `0` 免费 | 改 0 时数值等同「按晚」，只改配置不改代码      |
| 四处一致               | 结算页 = 订单 `total_fee` = 支付成功页 = 导出 / 统计           | 一条用例锁死（见第八节 U1）             |

**按天的三个必然后果，必须在页面和协议里写明**：



1. **今天入住、明天离店 = 2 个照护日**（不是 1 晚）。短片寄养会比「按晚」报价贵约一倍，因此结算页不能只显示金额，要显示「共 N 个照护日（11-10 至 11-13，含离店当日）」。

2. **协议文案整段重写**：现文案「跨天寄养按晚计费：晚数 = 离店日期 - 入住日期」与按天冲突，改为「按照护日计费：计费日数 = 离店日期 − 入住日期 + 1，入住日与离店日均计 1 日，同日寄养按 1 日计」。

3. **前端&#x20;**`utils/util.calcDays`**&#x20;要加&#x20;**`+1`（现在少算一天）；支付成功页、导出、统计都读后端 `total_fee`，无需改动。

**为什么按天的改动量反而更小**：后端 `FosterOrderService.calcTotalFee` 现在就是「离店 − 入住 + 1」，与按天完全一致；种子订单 `FO20261025002` 的 960 元、历史订单金额、单元测试「10-01→10-05 = 5 天 500 元」都不用动。要改的只有前端一处公式和一整段协议文案。

**计价结构（谁定价、按什么单位）**：定价不是写死在代码里的数字，而是「档位价 × 日数 + 服务明细 + 规则加减」。现状与目标差在这三处：



| 价格项    | 数据来源                                                              | 计价单位          | 现状                                |
| ------ | ----------------------------------------------------------------- | ------------- | --------------------------------- |
| 房费     | `foster_price.price_per_day`，管理员在「寄养价位」维护（标准 60 / 舒适 80 / 豪华 120） | 元 / 照护日       | 已有；下单只选档位，不能改价                    |
| 增值服务   | 现在**硬编码在前端**（洗护 30 / 遛宠 20 / 接送 40），后端没有价目表                       | 元 / 次 或 元 / 日 | 页面显示另收，后端**不计费**，只把服务名拼进 `remark` |
| 节假日加价  | `biz_rule.holiday.markup`                                         | 倍率            | 无                                 |
| 优惠 / 券 | `coupon.discount` + 长住规则                                          | 元             | 前端减了 20，后端不抵扣也不核销                 |
| 押金     | `foster_order.deposit_fee`（默认 0）                                  | 元             | 无（协议写「无押金」）                       |

目标口径：`total_fee = 房费 + Σ(服务单价 × 数量) + 节假日加价 + 医疗 + 超时 + 赔偿 − 优惠`。数量按服务项的计价单位定：



* `unit_type = day`（「每日遛宠」20 元 / 日）→ 数量 = `charge_days`，**必须乘日数**。现在只加一次 20，名称写「每日」、钱按一次收，是计价口径错误。

* `unit_type = once`（「洗护美容」30、「上门接送」40 / 单程）→ 数量 = 1。

服务要**另收**，且必须落 `foster_bill_item` 明细：洗护耗材、接送油费、遛宠人力都是独立成本，不算房费的一部分；但也不能只在页面上显示 —— 否则就是「结算页 880 + 50 = 930，订单实收 960」这种两边都解释不清的账。

### 2.1 房间与房态（P0-1）



```sql
-- 房间（物理房位，与价位档位多对一：豪华间可能有 3 间）
CREATE TABLE IF NOT EXISTS foster_room (
  room_id     BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '房间ID',
  store_id    BIGINT NOT NULL COMMENT '门店ID',
  room_no     VARCHAR(20) NOT NULL COMMENT '房号/笼位号，如 A-01',
  price_id    BIGINT NOT NULL COMMENT '对应价位档位ID',
  room_type   VARCHAR(20) NOT NULL COMMENT '类型: 犬舍/猫舍/套房',
  capacity    INT NOT NULL DEFAULT 1 COMMENT '同住上限(只)',
  status      VARCHAR(20) NOT NULL DEFAULT '空闲' COMMENT '状态: 空闲/已预订/在住/待清洁/维修/隔离',
  sort        INT DEFAULT 0 COMMENT '排序',
  remark      VARCHAR(255) COMMENT '备注',
  deleted     INT NOT NULL DEFAULT 0 COMMENT '逻辑删除: 0正常 1删除',
  create_time DATETIME COMMENT '创建时间',
  UNIQUE KEY uk_store_room (store_id, room_no),
  KEY idx_price (price_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='寄养房间表';

-- 房间占用（一条订单一条，区间半开）
CREATE TABLE IF NOT EXISTS foster_room_booking (
  booking_id     BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '占用ID',
  room_id        BIGINT NOT NULL COMMENT '房间ID',
  order_id       BIGINT NOT NULL COMMENT '订单ID',
  occupy_start   DATE NOT NULL COMMENT '占用开始(含)',
  occupy_end     DATE NOT NULL COMMENT '占用结束(不含，通常是离店日)',
  status         VARCHAR(20) NOT NULL DEFAULT '锁定' COMMENT '状态: 锁定/占用/释放',
  create_time    DATETIME COMMENT '创建时间',
  UNIQUE KEY uk_room_order (room_id, order_id),
  KEY idx_room_range (room_id, occupy_start, occupy_end)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='房间占用表';
```

**防超订查询**（下单前必跑，返回 1 即不可订；下面是 MyBatis 片段，`#{}` 是参数占位，**不能直接喂给 mysql 客户端**）：



```sql
SELECT 1 FROM foster_room_booking b
JOIN foster_room r ON r.room_id = b.room_id AND r.deleted = 0
WHERE r.price_id = #{priceId}
  AND b.status <> '释放'
  AND b.occupy_start < #{occupyEnd}
  AND b.occupy_end > #{occupyStart}
LIMIT 1;
```

> MySQL 表达不了「区间不重叠」的约束，所以用
> **应用层校验 + 行锁**
> （
> `SELECT ... FOR UPDATE`
> 或 Redis 分布式锁按 room_id）。只靠前端置灰一定会被绕过。

## 五、规则可计算化（把「承诺」写成公式）



| 规则    | 公式 / 判定                                                                                       | 落点                                      |
| ----- | --------------------------------------------------------------------------------------------- | --------------------------------------- |
| 计费日数  | `charge_days = max(1, DATEDIFF(离店, 入住) + 1)`（含离店当日）                                           | 下单、离店、导出                                |
| 应收房费  | `单价 × charge_days + 节假日加价`                                                                    | `bill_item(ROOM)`                       |
| 增值服务  | `Σ(service_item.price × 数量)`；`unit_type=day` → 数量 `charge_days`，`once` → 1                    | `bill_item(SERVICE)`，汇总 `extra_fee`     |
| 优惠抵扣  | `min(券面额, 应收)`；核销后 `coupon.status=USED` 且写 `used_time`，订单记 `coupon_id`                        | `bill_item(DISCOUNT)`，汇总 `discount_fee` |
| 押金退还  | 退房时 `deposit_fee` 原路退，先扣赔偿、欠费、超时费，结余返还                                                        | 离店结算                                    |
| 定金    | `round(房费 × deposit.ratio, 2)`                                                                | 下单写 `deposit_fee`                       |
| 阶梯退定金 | `h = 入住日 00:00 − 取消时刻`；取 `refund.ladder` 第一个满足 `h >= h_i` 的 `r`，退款 `= 定金 × r`                 | 取消接口                                    |
| 逾期手续费 | `h < refund.free_hours` 且取消 → 扣 `late.fee_days` 日房费                                           | 取消接口                                    |
| 超时费   | `min(ceil(超时小时) × overtime.hour_fee, 一日房费)`                                                   | 离店结算                                    |
| 提前离店  | `实住日 = max(1, DATEDIFF(实际离店, 入住) + 1)`，差额退款；提前离店**不退定金**                                      | 离店结算                                    |
| 弃养处置  | 离店日 + `abandon.hours` 未接、且通知记录 ≥2 次 → 生成「待处置」工单，**不自动处置**                                     | 定时任务                                    |
| 拒收判定  | 命中任一：未免疫 / 有效期外、幼犬（<4 月）、术后 7 天内、传染病、体外寄生虫、发情期 → 阻断下单 + 写 `pet_reject`                        | 下单与入店                                   |
| 喂药加收  | `medication.daily_fee × charge_days`                                                          | 增值明细                                    |
| 送医授权  | `notify_customer=1` 且 `notify_channel!=null` 才可填 `vet_authorized_by`；费用进 `bill_item(MEDICAL)` | 异常接口                                    |
| 欠费违约金 | `欠费 × 日费率 × 逾期天数`（日费率进 `biz_rule`）                                                            | 结算                                      |

模糊的地方要显式写死，例如：**提前离店是否退定金**、**超时费是否与加住一天二选一**。这两条现实门店各有做法，必须门店选一个，否则代码里永远有歧义。

## 十、合规基线（合规第一）

> 这一节把「合规」从 9.4 的留痕建议抬成
> **系统硬门槛**
> 。系统不替门店判断它有没有经营资质，只做三件事：
> **拦不该做的、记必须留的、出事能证清责任。**

### 10.1 效力边界先划清



| 档位    | 依据                         | 效力                  |
| ----- | -------------------------- | ------------------- |
| 法律    | 民法典、个人信息保护法、动物防疫法          | 全国有效，必须遵守           |
| 地方规定  | 如北京对动物寄养场所的防疫要求            | 仅当地，跨省不能照搬          |
| 标准与惯例 | 团体标准（草案，非强制）、境外牌照条件、门店协议样本 | 商务惯例，可作行业参照，不能当法规引用 |

写论文或答辩时按这三档说话：**法律说 "必须"，地方规定说 "当地要求"，标准说 "行业做法"**。

### 10.2 三条民事责任线（为什么合规排在钱前面）



| 依据          | 原文要点                                     | 对系统的硬要求                                          |
| ----------- | ---------------------------------------- | ------------------------------------------------ |
| 民法典第 1245 条 | 「饲养的动物造成他人损害的，动物饲养人**或者管理人**应当承担侵权责任」    | 寄养期间门店是**管理人**。出事时要证明 "已尽管理义务"，只有交接单、巡视、异常处置记录能证 |
| 民法典第 1246 条 | 「未对动物采取安全措施造成他人损害的…… 应当承担侵权责任」           | 遛放必须牵引、猫犬分区、烈性犬拒收 —— 这些 "安全措施" 必须留记录，否则举证时无话可说   |
| 民法典第 1247 条 | 「禁止饲养的烈性犬等危险动物造成他人损害的…… 应当承担侵权责任」（无免责事由） | 下单与入店都要能识别并拦截烈性犬，拒收必须留证                          |
| 民法典第 1249 条 | 「遗弃、逃逸的动物在遗弃、逃逸期间造成他人损害的，由动物原饲养人或者管理人承担」 | 走失要立刻留时刻与处置记录（`foster_incident.category=走失`）     |

一句提醒：**协议里的免责条款对第 1247 条无效**。别把 "客户签了免责声明" 当成安全垫。

### 10.3 防疫与证照



| 依据                             | 原文要点                                                               | 系统落点                                                                             |
| ------------------------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 动物防疫法第 7 条                     | 从事动物饲养、隔离等，应做好「免疫、消毒、检测、隔离……」并承担防疫责任                               | 免疫证明核验、消毒台账、隔离区                                                                  |
| 第 24 条                         | 防疫条件含「有与其规模相适应的**执业兽医**或者动物防疫技术人员」；「有完善的**隔离消毒**、购销台账、**日常巡查**等制度」 | `staff_cert`（执业兽医）、`foster_disinfection_log`、`foster_care_log`（日常巡查）、购销台账（物品出入）  |
| 第 25 条                         | 开办动物饲养场和**隔离场所**应经审查取得**动物防疫条件合格证**                                | `store_license` 留档 + 到期提醒。**是否需办证、按什么口径认定，由当地农业农村部门定，系统只留档，不下结论**                |
| 第 31 条                         | 「发现动物染疫或者疑似染疫的，应当**立即**…… 报告，并**迅速采取隔离**等控制措施」                     | `foster_incident` 增「疑似传染病」类别 + 报告对象 / 报告时间必填 + 立即置 `room.status='隔离'` + 一键导出同区宠物 |
| 动物防疫法第 62 条 +《动物诊疗机构管理办法》第 5 条 | 从事动物诊疗活动的机构应取得**动物诊疗许可证**，并在核定范围内开展                                | 全职兽医只做评估、处置复核、送医判断；诊断、处方、注射、手术一律转持证机构，系统只存转诊单与外部处方编号 `prescription_ref`          |

### 10.4 个人信息（个保法）



| 依据     | 要点                      | 系统落点                                   |
| ------ | ----------------------- | -------------------------------------- |
| 第 6 条  | 「限于实现处理目的的最小范围，不得过度收集」  | 客户表只留姓名、手机、地址；**不采身份证、不采人脸**           |
| 第 13 条 | 为履行合同所必需可不经单独同意，但告知义务仍在 | 下单页与隐私说明告知                             |
| 第 17 条 | 必须告知处理目的、方式、种类、**保存期限** | 隐私说明写明「寄养档案保存 2 年」                     |
| 第 19 条 | 「保存期限应当为实现处理目的所必要的最短时间」 | `biz_rule.retention.days = 730`，到期归档脱敏 |

三条落地细节：



* **脱敏**：列表与导出把手机号打码（`138****8001`），看完整号需二次确认并记日志；

* **导出留痕**：任何客户 / 宠物 / 订单 / 档案导出写 `data_export_log`（谁、何时、导了什么、多少条、用途）；

* **不碰人脸**：人脸识别另有专门办法（要求单独同意、不得联网传输），寄养场景没有正当必要，直接不做。

### 10.5 六条硬控制（系统强制，不靠人记）

| - | ------------------------ | ------------------------ | --------------- | ------------------------------------------------------ |
| 1 | 无有效免疫证明不得寄养              | 下单**和**入店两处都校验（只拦一处等于没拦） | 下单 400 + 入店 409 | `pet_cert.expire_date >= 入住日`、`audit_status='通过'`      |
| 2 | 烈性犬、术后 7 天内、发情期、体外寄生虫拒收  | 下单 / 入店                  | 阻断 + 提示原因码      | `pet_reject`                                           |
| 3 | 猫犬不混区                    | 派房                       | 阻断选房            | `foster_room.room_type` 与宠物种类匹配                        |
| 4 | 入店交接四项齐（称重、照片、物品清单、客户签字） | 入店                       | 缺一项不许入店         | `foster_handover` 四个字段非空                               |

### 10.6 举证包：出事时能立刻交出去什么

一份订单档案 = **免疫 / 驱虫证明** + **入店交接单（体重、照片、物品、签字）** + **每日三班巡视** + **异常与通知记录** + **送医授权** + **消毒记录** + **账单明细**。

接口：`GET /api/orders/{id}/archive` 返回 PDF（必要时附照片原图打包 ZIP），先写 `data_export_log` 再返回。

隔离追溯（同期间同房型住过谁）—— 出传染病时这条要能 1 分钟出结果（MyBatis 片段，`#{}` 为参数占位，不能直接喂给 mysql 客户端）：



```sql
SELECT DISTINCT o2.order_id, p2.name AS pet_name, c2.name AS owner, c2.phone
FROM foster_room_booking b1
JOIN foster_room r1      ON r1.room_id = b1.room_id
JOIN foster_room_booking b2 ON b2.room_id = b1.room_id AND b2.order_id <> b1.order_id
JOIN foster_order o2     ON o2.order_id = b2.order_id
JOIN pet p2              ON p2.pet_id = o2.pet_id
JOIN customer c2         ON c2.customer_id = p2.customer_id
WHERE b1.order_id = #{orderId}
  AND b1.occupy_start < b2.occupy_end
  AND b1.occupy_end   > b2.occupy_start;
```

## 十一、人员细分落地（岗位・能力・资质）

### 11.1 为什么不新增系统角色

登录侧只有两类主体：`sys_admin`（管理员）与 `staff`（员工），所有员工共用 `STAFF` 权限集。人员细分**不动这两个角色**，只在员工内部按岗位判能力组。三个理由：



* 角色一动，`SecurityConfig`、前端路由守卫、现有接口的授权判断全要重写，回归面远大于收益；

* 一人多岗在小门店是常态（店长兼前台、护理员兼美容），角色模型表达不了；

* 岗位是人力资源属性，权限是系统属性，绑死之后每次调岗都要改代码。

一句话：`positions`**&#x20;决定能做什么，**`cert`**&#x20;决定能签什么字，**`shift`**&#x20;决定今天谁负责。**

### 11.2 岗位字典



| 代码       | 中文显示               | 能力组      | 可兼任 | 典型职责                        |
| -------- | ------------------ | -------- | --- | --------------------------- |
| `OWNER`  | 店长／管理员（admin 落点） | A+B+C    | 与前台 | 经营配置、员工账号与系统管理、报表、审批、兼任签字 |
| `FRONT`  | 前台                 | B        | 与店长 | 建档、收银、入离店登记，**不做健康判定**      |
| `CARE`   | 护理员                | C        | 与兽医 | 喂食、遛放、三班巡视、健康记录             |
| `GROOM`  | 美容师                | C（仅洗护核销） | 是   | 洗护美容核销，不碰订单与账目              |
| `DRIVER` | 外勤接送               | —        | 与护理 | 接送任务                        |
| `VET`    | 兽医（**全职在岗**，本项目已定） | C + 判定权  | 与护理 | 入离店健康评估、健康判定、隔离建议、送医授权、处置复核 |

存储：`staff.positions` 存**代码**（如 `OWNER,FRONT`），中文只是显示映射。**不要把中文值写进权限判断**—— 改一次显示名就会静默失效。

> 本文其余 SQL 示例为便于阅读用了中文值（
> `护理员`
> /
> `兽医`
> ），采纳代码制后等价替换即可。

保存侧校验：每个逗号片段必须命中白名单常量集合，出现非法值直接 400；不要只靠数据库 `CHECK`，MySQL 对逗号串的约束语义太弱。

**fail closed**：`positions` 为空时 `FIND_IN_SET` 返回 NULL、条件不成立，即无任何敏感权限。这是有意设计，不给兜底。

### 11.3 能力组判定（三个值，不是一张矩阵）



| 能力组     | 由谁获得                              | 管什么                  |
| ------- | --------------------------------- | -------------------- |
| A 经营配置  | `OWNER`                           | 房间、价位、规则、排班、资质、报表、导出 |
| B 接待与结算 | `OWNER`、`FRONT`                   | 建档、下单、入离店、收银退款、账单    |
| C 照护与记录 | `OWNER`、`CARE`、`VET`、`GROOM`（仅核销） | 巡视、健康记录、异常、交接签字      |

实现约定（只定契约）：方法级注解 `@RequireCapability({"B"})`，取值并集；拦截器从登录态取 `staffId` → 查 `positions`（缓存 5 分钟）→ 映射能力组 → 缺则返回 `Result{code:403, message:"当前岗位无此操作权限"}`；`sys_admin` 直接放行。前端按同一映射隐藏按钮，但**后端必须再判**，前端隐藏不算权限。

第四节接口表里三处易错，单独点出来：



* `POST /api/orders`：建单是 B，但**改价 / 免单是 A**，避免前台随意让价；

* `POST /api/orders/{id}/care-log`：C，且 `positions` 必须含 `CARE` 或 `VET`（见 11.4）；

* `GET /api/export/*`：A。客户手机号整表导出不该在前台手里。

### 11.4 资质校验：五个判定点



| # | 动作                     | 岗位前置                                              | 资质前置                                                                                  | 落库字段                                                          |
| - | ---------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1 | 填巡视 / 健康记录             | `CARE` 或 `VET`                                    | 无（有护理培训优先录用）                                                                          | `foster_care_log.recorder_id`、`pet_health_record.recorder_id` |
| 2 | 异常升级（隔离、送医）            | `VET` 且**当日在岗**（紧急可先由 `OWNER` 记录并标 `emergency=1`） | **授权须&#x20;**`cert_type='执业兽医'`**&#x20;且&#x20;**`valid_to >= 今日`；紧急通道要求 24 小时内补签，逾期红标 | `foster_incident.vet_authorized_by`、`vet_authorized_at`       |
| 3 | 入离店交接签字                | `FRONT` 或 `CARE`                                  | 无                                                                                     | `foster_handover.signer_id` + `signer_position` 快照            |
| 4 | 增值服务核销                 | 洗护→`GROOM`；接送→`DRIVER`；遛宠→`CARE`                  | 无                                                                                     | 结算时校验 `foster_bill_item`                                      |
| 5 | 入店 / 离店健康评估（能否寄养、能否带走） | `VET` 且**当日在岗**                                   | `cert_type='执业兽医'` 且有效                                                                | `pet_health_record.verified_by`（`type` 为入店 / 离店记录时必填）         |

三条硬约束：



* **送医授权不能只看岗位**：`positions` 含 `VET` 但人已离职、证已过期时，判定权必须立即失效。用 `valid_to >= CURDATE()` 判，**不给宽限期**。

* **签字人岗位要快照**：`signer_position` 记当时岗位，不 join 现查 —— 人调岗后历史单据不能被改写。

* **先沟通后授权**：`foster_incident.notify_customer=1` 且 `notify_channel` 非空，才允许填授权人。

缺班查询（今日在住订单 × 早中晚，找缺失）：



```sql
SELECT o.order_id, t.shift FROM foster_order o
CROSS JOIN (SELECT '早' AS shift UNION ALL SELECT '中' UNION ALL SELECT '晚') t
LEFT JOIN foster_care_log l ON l.order_id = o.order_id AND l.log_date = CURDATE() AND l.shift = t.shift
WHERE o.status = '寄养中' AND l.care_log_id IS NULL;
```

今日主责护理员的查询见 2.9。

兽医是否在岗，单独查（全职不等于自动在岗，排班才算）：



```sql
SELECT CURDATE() AS d,
       IFNULL(SUM(CASE WHEN FIND_IN_SET('VET', st.positions) AND st.status = 1 THEN 1 ELSE 0 END), 0) AS 今日在岗兽医
FROM staff_shift s
JOIN staff st ON st.staff_id = s.staff_id
WHERE s.shift_date = CURDATE();
```

`今日在岗兽医 = 0` → 首页红标「今日无持证兽医」，处置类记录与送医授权当班即关闭。空表实测返回 0（`IFNULL` 兜住 `SUM` 的 NULL，避免红标判不出来）。

### 11.10 健康档案谁能写、谁能签：三层，不是一刀切（宠物医生必须有）

先把现状摆出来（都核过代码和 `schema.sql`）：



| 事实                                                    | 结论                                               |
| ----------------------------------------------------- | ------------------------------------------------ |
| `pet_health_record` 字段只有：体温、精神、食欲、排便、皮肤、异常情况、处理措施、记录人 | 它记的是**观察与处置**，没有诊断、处方、用药、疫苗判定 —— 本质是观察记录，不是病历    |
| 整类 `@PreAuthorize("hasRole('STAFF')")`                | 前台、清洁、美容、护理**任何员工**都能写「处理措施」，写 "已喂药、已处理" 不需要任何资质 |
| `recorder_id` 只存 `staff_id`                           | 人调岗或离职后，无法证明当时是什么岗位、有没有资质                        |
| 没有复核人字段                                               | 处置结论只有一个人说过，没有第二人背书                              |
| `sys_admin`（店长邮箱账号）访问 `/api/health-records` 返回 403    | 权限方向反了：该看的看不到，不该判断的全都能写                          |

所以正确的问法不是 "有健康档案要不要配兽医"，而是 "**档案里的哪一层内容需要资质背书**"。分三层：



| 层      | 内容                    | 谁能写                                              | 是否需要兽医                   |
| ------ | --------------------- | ------------------------------------------------ | ------------------------ |
| L1 观察层 | 体温、精神、食欲、排便、皮肤、体重、照片  | `CARE` 或 `VET`，当班即可                              | 不需要。这是每日三次巡视的产出，兽医不可能亲自做 |
| L2 处置层 | 异常情况、处理措施（喂药、擦药、隔离观察） | `CARE` 记录 + `VET`**&#x20;复核签署**                  | 需要复核，但不必现场               |
| L3 病历层 | 诊断、处方、疫苗判定、传染病结论、送医决定 | 仅持证 `VET`（`cert_type='执业兽医'` 且 `valid_to >= 今日`） | 必须是兽医                    |

一句话：**档案里出现处置与诊断时，必须由持证兽医签字背书**。现在的毛病是三层压在一张表、一个权限里 —— 要么全开（现状），要么全锁（门店跑不动）。

落地只有三步，改动很小：



1. 字段补齐（见 2.13）：`recorder_position`（岗位快照）、`verified_by`（复核兽医）、`verified_at`（复核时间）。

2. 校验规则：写 L1 只需 `positions` 含 `CARE`/`VET`；`abnormal` 或 `treatment` 非空时，`verified_by` 必须非空且该兽医当时持证有效，否则接口直接拒绝（fail closed，不给 "先存后补" 的口子）。

3. `OWNER` 只读可审：店长能看全部档案与复核状态、能催办，但**不能替兽医签**—— 签了就变成店长的判断，责任链反而更糊。

**本项目已定：宠物医生全职在岗。** 不再考虑外协或 "挂靠合作医院代签" 的形态 —— 全职意味着每天都在场，入离店评估、处置复核、送医授权都有人当场签字，不必等外部人回复。落到系统里的硬要求是：`staff` 中有一个 `positions` 含 `VET`、`staff_cert` 有有效期内的执业兽医证、`status=1` 的账号，**并且纳入&#x20;**`staff_shift`**&#x20;排班**（有证不等于在岗，见 U21）。让店长代填 `verified_by` 的做法**不采用**—— 代签等于店长在做医疗判断，责任链恰好断在最需要专业背书的那一环。

**但全职兽医不能把店变成诊所。** 动物防疫法第 62 条规定，从事动物诊疗活动的机构应当申请**动物诊疗许可证**；《动物诊疗机构管理办法》（农业农村部令 2022 年第 5 号）第 5 条再次明确国家实行动物诊疗许可制度、须在核定范围内开展。宠物旅馆不是诊疗机构，所以全职兽医在这里能做与不能做要划清：



| 能做（店内，属健康管理与照护）                                   | 不能做（属诊疗活动，须持证机构） |
| ------------------------------------------------- | ---------------- |
| 入店 / 离店健康评估、体温皮肤精神检查                              | 诊断、开具处方          |
| 处置复核（非药物处置：清洁、补液观察、隔离待诊）                          | 注射、输液、手术、麻醉      |
| 判断是否需要送医、写转诊单                                     | 在店内出售或使用处方药      |
| 依据外部处方执行喂药（只记 "按某院处方执行"，处方编号落 `prescription_ref`） | 自己写用药方案、改剂量      |

一句话：**系统里不允许出现 "本院诊断" 和 "院内处方"**，只允许出现 "评估结论、处置记录、转诊单、按外部处方执行的记录"。这既保证档案有专业背书，也不会让寄养店踩到无证诊疗。

宠物医生要签的不止 "复核一下"，是四个环节：



| 环节                                 | 谁签                                        | 不签的后果                                          |
| ---------------------------------- | ----------------------------------------- | ---------------------------------------------- |
| 入店健康评估（能否寄养、是否拒收、体温 / 皮肤 / 精神是否达标） | `VET`                                     | 带病入店，隔离与责任都说不清；拒收记录也失去依据                       |
| 寄养期处置复核（用药、擦药、隔离观察）                | `VET`                                     | 员工写了 "已处理"，出事证明不了是谁的判断                         |
| 隔离 / 送医授权                          | 持证 `VET`（紧急可先由店长记 `emergency=1`，24 小时内补签） | 无法证明 "发现即处置"，民法典 1245 / 1246 所谓 "尽到管理义务" 举证不成立 |
| 离店健康结论（建议做）                        | `VET`                                     | 客户接回病宠时，责任分界说不清                                |

**没有在岗兽医时怎么办**（离职、证过期、当日未排班）：处置类记录与送医授权一律拒收（fail closed），首页红标「今日无持证兽医」；仍可做的是 L1 观察与喂养。这样系统不会因为缺人默认放宽，也不至于因为缺人整店停摆。

配套两条：入店评估落 `type='入店记录'` 且 `verified_by` 必填（见 2.13）；执业证到期前 30 天进待办，到期当天判定权失效，不给宽限期。

### 11.11 三端分工与拍照留痕（员工用手机，不是把员工搬进小程序）

**结论：不清空 Web，也不让员工整体改用小程序，按职责分三端。**

| 端 | 谁用 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| 顾客小程序（现有 11 页） | 客户 | 选房下单、支付、订单、宠物档案、照护动态只读、评价 | 任何员工操作 |
| 员工端（手机；同一小程序内按角色分流） | 护理员、兽医、美容师、外勤 | 今日待办、入离店交接、巡视打卡拍照、异常上报、服务核销 | 收银退款、报表导出、价格与规则配置 |
| 管理端 Web（现有） | 店长、前台 | 订单排期、收银对账、客户与宠物档案、健康档案复核、排班与资质、规则配置、统计导出 | 逐次巡视拍照（现场动作不该回工位补录） |

为什么不能反过来：

- **拍照是现场动作**。犬舍里那一刻的气温、爪垫颜色、呕吐物形状，回工位再补拍就变成"事后摆拍"，举证价值基本归零；而兽医要靠这些照片判断是否隔离、是否送医。
- **桌面动作搬不动**。批量排期、收银对账、退款、导出报表、价格与规则配置，在 5 寸屏上没有可用形态，硬搬只会加误操作。
- **举证要时间与地点**。手机拍摄天然带拍摄时间，配上订单号、工号、班次，才构成完整的一条留痕链；Web 上传的图片做不到"那一刻在犬舍"。

**员工端页面清单（5 个，够用即可）**

| 页面 | 数据来源 | 关键动作 | 判定 |
| --- | --- | --- | --- |
| 今日待办 | 11.5 四张待办卡 | 领取任务、标记完成 | 需 `CARE`/`VET`/`GROOM`/`DRIVER` |
| 入店 / 离店交接 | `foster_handover` | 拍正面照、称重、四项体表检查、客户签字 | 需 `FRONT`/`CARE`，存 `signer_position` |
| 巡视打卡 | `foster_care_log` | 拍照、填体温/精神/食欲/排泄、异常描述 | 需 `CARE`/`VET`（能力组 C） |
| 异常上报 | `foster_incident` | 拍患处、选等级、通知客户、升级兽医 | 处置须 `VET` 且**当日在岗**（11.4 判定点 2） |

**拍照规则（业务要求，不是技术偏好）**

1. 每班次至少 1 张；`abnormal` 非空必须 2 张，含患处近照。

### 11.12 每个岗位做什么、能进哪些页面

**一条原则先说清**：页面权限只决定「看不看得到」，真正的边界在后端接口。菜单隐藏是礼貌，403 才是墙——所以每个页面背后必须有对应的能力组校验，不能只靠前端过滤。

3. **最小必要原则跟着入口一起走**——美容师只看洗护单、外勤只看接送单、护理员不碰账目与客户病史（个保法第 6 条）；入口从 Web 换到小程序后，这条约束在小程序页面权限表（下表）与后端 `StaffAuth` 中继续落实，不因没有 Web 页而放宽。

#### 岗位间交接全景（谁交给谁）

```
客户 ──下单收款──> 前台 ──入店交接──> 护理/兽医(入店评估)
                                        │ 巡视/异常
                                        ├──> 兽医(处置/授权) ──> 护理(执行)
                                        ├──> 美容(洗护) / 外勤(接送) / 护理(遛宠)
                                        │ 离店评估(兽医签署)
客户 <──结算评价── 前台 <──离店交接── 护理
```

- 四个签字环节：入店交接（FRONT+CARE）、离店交接（FRONT+CARE）、入/离店健康评估（VET 且当日在岗）、送医授权（VET 且当日在岗）。
- 三条状态主线：**订单** 待入店 → 寄养中 → 已完成（/已取消/已退款）；**异常** 上报 → 待定级 → 已处置（/隔离/送医）；**增值服务** 待核销 → 已核销（按岗位）。
- 断点保护：任何「需 VET 而当日无兽医」的步骤一律 fail closed（不降级给护理代签），只允许 OWNER 记 `emergency=1` 兜底、24 小时内补签。

### 11.14 同一账号、多端数据同步（新增硬要求）

同一个员工账号（`sys_user`）在 Web 与员工端登录，**数据必须实时同源**：

- **一份数据**：交接、巡视、异常、核销、账单、排班只有一份（同一后端、同一张表），员工端写入 → Web 端立即可见，反之亦然；不存在「手机记一份、电脑记一份」。
- **同一身份**：岗位（`positions`）、资质、能力组从同一份数据取；两端登录返回相同角色与权限，一端调岗另一端立即生效。
- **待办同源**：今日待办是同一个聚合查询，两端看到的缺班、待评估、待核销一致；一端处理完，另一端消失。
- **会话边界**：两端共用账号与权限体系（同一 JWT 签发方）；密码修改、禁用立即双端生效。
- **验收**：员工端核销遛宠 → Web 端「寄养服务记录」立即显示已核销；Web 端给护理员调岗 → 员工端下次登录即按新岗位显示页面。
