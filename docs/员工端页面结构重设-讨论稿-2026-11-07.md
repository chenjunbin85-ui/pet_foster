## 〇、结论先说

「像网页」不是配色、圆角或字体的问题——去壳（P0-1）之后外观已经是原生栏 + 暖色卡片。**网页感来自三处结构，而不是视觉**：

| 层 | 现状的结构 |
|---|---|
| **页面骨架** | 18 个原型页共用一套母版：`顶部订单条 → 卡片堆 → 底部固定大按钮 → 提交后全屏成功`。这是 Web 后台「详情页 / 编辑表单」的骨架，只是竖过来放进手机。 |
| **内容编排** | 卡片内部按**数据库字段顺序**一行一字段平铺（体温、精神、食欲、排便、皮肤、异常描述），而不是按现场**判断顺序**组织；正常项和异常项一样占位。 |
| **层级** | 19 页里 17 页是同级二级页，全部 `navigateTo` 进入，返回栈就是导航；没有「队列 → 详情 → 作业」的中间层，任务卡直接跳表单。 |
| **闭环** | `submit()` 统一把页面翻成 `success=true` 全屏成功态，只能「返回」；不更新队列、不进入下一单、不消红点。等于 Web 的「保存成功，请关闭页面」。 |

**所以补底部导航、补「我的」只是这两个结构缺陷的**结果**，不是解法本身。** 真正的顺序是：先定页面类型（4 套母版）→ 再定每页内容编排（动作流）→ 再定层级（队列/详情）→ 最后才是导航与个人中心。否则加了 tab，点进去仍是同一套后台表单。

## 一、现状骨架解剖（证据）

### 1.1 19 页只有 5 种骨架，其中 15 页是同一种

| 骨架 | 页面 | 结构 |
|---|---|---|
| A 入口页 | `home` | 身份卡（含 3 个数字）→ 岗位宫格 → 分组菜单 → 脚注 |
| B 岗位台 | `c1 / v1 / g1 / d1` | 身份条 → 统计卡（大数字 + 三段）→ 任务卡列表（每卡 4 行 + 2 按钮） |
| C 作业表单 | `c2 c3 c4 c5 / v2 v3 v4 v5 / g2 / d2` | 订单条 → 宠物卡 → N 个「标题 + 字段行」卡 → 照片 → 固定底栏 |
| D 核销 | `c6 / g3 / d3` | 订单信息 → 核销项目 → 服务记录 → 凭证照 → 固定底栏 → 成功态 |
| E 个人中心 | `mine` | 身份卡（3 行后台字段）→ 班次卡 →（兽医）资质卡 → 菜单 2 组 |

C 类 10 页共用 `utils/staff-page.js` 同一套数据模型：`title / readOnly / tab / form / photos / d(示例订单) / success`。**页面 JS 只声明字段与 `build()`，交互全是「填表 → 提交」**——这是表单生成器，不是移动端作业工具。

### 1.2 以「巡视打卡 c2」为例，把骨架画出来

```
┌ 订单条 ────────────────────────────────┐
│ FO20261008001 · 旺财 · B-108 · 寄养中      ← 后台面包屑，非现场语言
└────────────────────────────────────────┘
┌ 宠物卡（头像 + 名 + 品种 + 房号 + 巡视次数）┐
└────────────────────────────────────────┘
┌ 巡视数据 ───────────────────────────────┐
│ *体温   [ 38.5 ] ℃                        ← 一行一字段
│ *精神   (正常) (萎靡) (亢奋)               ← 每个选项一枚小胶囊
│ *食欲   (正常) (少食) (拒食)
│ *排便   (正常) (腹泻) (便秘)
└────────────────────────────────────────┘
┌ 观察记录 ───────────────────────────────┐
│  皮肤   [____________________]
│  异常   [____________________]             ← 与服务端字段一一对应
└────────────────────────────────────────┘
┌ 现场照片（0/6，横排小格）┐
└────────────────────────────────────────┘
[========== 提交巡视 ==========]              ← 固定底栏，约占 1/6 屏
```

**问题不在字段对不对，而在四件事：**

1. **主语叠了两层**：顶部「订单号 / 房号 / 寄养中」是运营视角，中间「旺财」是现场视角。护理员在犬舍里只关心「哪只、第几次」，订单号对他没有意义（截图 14 顶部灰条）。
2. **字段顺序是表结构**：真实动作是「先看整体正不正常，不正常才记细节」；现在的顺序要求把四项全部逐行读完才能判断，正常的一次也要滑两屏。
3. **照片在页尾**：而业务规则要求「每班至少 1 张，异常必须 2 张含患处近照」（方案 11.11 拍照规则 1）。**把照片放在提交按钮之前、又被固定底栏压住（截图 16/18 可见），等于把必填证据藏在最后一屏**——结构顺序与业务规则相反。
4. **主操作要滚动才看见**：固定底栏在首屏就占掉约 1/6 屏，长表单要滑 2 屏才露出「提交」。

### 1.3 内容组织：字段清单 vs 动作流

| 现状内容块 | 现场真实顺序 | 建议结构 |
|---|---|---|
| 订单号 / 房号 / 状态 | 哪只宠物、第几次、哪班 | 一行主语头（名字 · 房号 · 第 n 次/班次） |
| 四项体征逐行 | 一眼判断正常/异常 | 3–4 个大按钮组（单手可点），正常一键 |
| 皮肤 / 异常描述 | 异常才写 | 折叠区「+ 记一笔观察」，异常才展开 |
| 照片（页尾） | 拍完即传 | 照片提前，横滑缩略图 + 「待补传 n」 |
| 提交 → 成功页 | 提交 → 下一只 | 「提交并下一只」+ 回队列、状态更新 |

### 1.4 层级：17 页平铺，没有「队列」也没有「单」

- `pages/staff/` 下除 `home` / `mine` 外，17 页全是并列二级页，**无列表页、无详情页**。
- `home.js:79-85` 的任务卡点击直接 `navigateTo` 到表单页，并自动补 `?id=今日第一单`；`staff-page.js:270-275` 的 `orderId()` 在没带参时兜底取「今日待办第一单」。**用户点「开始巡视」时，系统替他决定了巡哪一只**——这不是移动端该有的上下文表达。
- PRD 3.3 五个页面里第一项就是「今日待办」，实现中被拆散进 `c1 / v1 / g1 / d1` 四个岗位台，且四个口径不一致（护理是「班次待办」，兽医是「在岗确认」，洗护/司机是「任务数」）。
- 结果：底部只能放「工作台 / 我的」两个 tab——**因为除了这两页，没有别的「一级页」可放**。

### 1.5 闭环：提交即终点

`staff-page.js:226-267` 的 `submit()` 流程是：上传照片 → `build()` → 调接口 → `success=true`。成功页模板固定为「图标 + 标题 + 说明 + 返回」。没有：队列回写、下一单入口、今日进度 +1、红点消除、离线补传队列。

对照方案 11.13：护理员一天 **3 次 × N 只**、兽医一天 4 评估 + 2 复核 + 离店签署、司机一天 6 趟。**业务是流水线，界面却是「一次一张单」的档案录入。**

### 1.6 「我的」的内容结构 = 账号信息页

`mine.wxml` 现状：身份（姓名/岗位/在岗 + **员工编号 / 账号角色 / 可用功能 13 项**）→ 今日班次（4 行）→ 执业资质（仅兽医）→ 我的工作（2 个入口）→ 账号（切换/帮助/关于/退出）。

- 「员工编号 / 账号角色 / 可用功能」是后台字段，用户不需要在手机上读「可用功能 13 项」。
- 真正该有的「我做过什么、我还欠什么、今天和谁一班、有没有消息」——**四项都没有**。
- 全端 grep `消息 / 通知 / 待办提醒` → 0；`我的记录` → 0；`当班同事` → 0。

## 二、目标结构

### 2.1 母版从 5 套收敛为 4 套（并明确各自职责）

| 类型 | 骨架（从上到下） | 用在哪 | 硬规则 |
|---|---|---|---|
| **一级·聚合页** | 一行班次/在岗状态 → 今日进度（完成 n / 待办 m / 待补传 k）→ 按时间轴分组的任务队列（可折叠）→ 底部 tab | 今日、我的 | 首屏必须能回答「我下一步做什么」 |
| **一级·岗位台** | 岗位徽标 + 一句职责 → 3 个数字（待做/进行/已完成）→ 队列卡列表（每卡 3 行 + 1 个主操作）→ 底部 tab | 护理/兽医/洗护/接送队列 | 一张卡只放一个动作 |
| **列表页** | 筛选行（日期/类型/状态）→ 摘要卡（头像 + 宠名 + 房号 + 状态标签 + 1 个动作）→ 上拉加载 | 任务列表、异常列表、我的记录 | 状态写在卡片上，不点进去才知道 |
| **作业页** | 单主语头（宠名 · 房号 · 第 n 次/班次）→ 已完成信息折叠 → 3–5 个待填项（异常才展开）→ 照片 → 底部主操作 + 次操作 | 巡视、护理记录、交接、评估、核销、拍照 | 主操作首屏可见；提交后「下一只 / 回队列」 |

### 2.2 内容组织八条规则（每条都能对到文档）

1. **一页一主语**：页面只回答「这只宠物现在要做什么」；人和班次压缩成顶部一行，不占卡片。（现状 c1/v1/g1/d1 顶部身份卡与主体抢注意力）
2. **顺序按判断，不按字段**：先「整体正常/异常」，再展开细节。（PRD 3.4 字段级权限说明各字段本就是分级填写）
3. **渐进披露**：正常项默认收起，异常才展开；护理一天 3 次、绝大多数是正常记录，不该每次滑两屏。（方案 11.13 护理员时序 3）
4. **必填证据前置**：照片不是页尾附件，是作业的一部分；异常必须 2 张含患处近照。（方案 11.11 拍照规则 1）
5. **一屏一动作**：主操作首屏可见；长表单拆「先提交、后补传」。（方案 11.11 弱网与重复提交）
6. **状态在卡上**：`待巡视 / 已巡 2/3 / 异常待复核 / 待核销` 直接写在列表卡与 tab 角标。
7. **闭环归队**：提交 → 回队列 → 卡片状态变 → 进度 +1 → 红点消；「提交并下一只」是默认路径。
8. **四态齐全**：空、加载、失败、离线（待补传 n 张）——现场弱网是常态，不是异常。

### 2.3 导航层：先解决「5 个名额」的硬约束

小程序 `app.json` 的 `tabBar.list` **只能 2–5 项**（自定义 tabBar 也一样）。现状用了 5 个：客户 3（首页/历史订单/我的）+ 员工 2（工作台/我的）。**再加任何一个员工 tab 就会超限**——这是「每个岗位视角不同」的第一道坎，必须先决策。

| 方案 | 做法 | 员工 tab | 客户 tab | 代价 | 评价 |
|---|---|---|---|---|---|
| **A 净值 3+2** | 客户压到 2（历史订单移入首页/我的入口），员工 3 | 今日 / 岗位队列 / 我的 | 首页 / 我的 | 动客户端底栏与入口 | 保原生，但改动了已定稿的客户端 |
| **B 自绘底栏 3+3（推荐）** | 去掉 `tabBar`，改为只在 6 个一级页挂载同一个 `staff-tabbar` 组件，切换用 `reLaunch` | 今日 / 岗位队列 / 我的 | 首页 / 历史订单 / 我的 | 需在 6 个一级页挂组件；`reLaunch` 会重建页面栈（数据反而更新鲜） | 不受 5 项限制、可按岗位渲染不同 tab；二级页本来就不该有底栏 |
| **C 双小程序** | 客户/员工各自 `app.json`，各 3–4 tab | 4 | 3 | 复制 `utils / styles`、两套发布 | 最干净，毕设规模偏重 |
| **D 维持 2 tab** | 不动 `app.json`，只把 `home` 首屏改为今日队列 | 今日 / 我的 | 3 | 改动最小 | 导航仍只有 2 项，用户诉求没真正解决 |

**推荐 B**，理由：
- 底部栏在真实小程序里**本来就只出现在一级页**，17 个二级页不该有——现在的「没有下导航栏」并不是缺陷本身，缺陷是**一级页只有 2 个、且不随岗位变化**。
- 方案 B 能把 tab 按岗位渲染：`CARE`=今日/巡视/我的、`VET`=今日/复核/我的、`GROOM`=今日/洗护/我的、`DRIVER`=今日/接送/我的、`OWNER·FRONT`=今日/工作台/我的。这才是「每个工作人员一个视角」。
- 自绘组件只在 6 个一级页挂载，不是 18 页，成本可控；避免重蹈「每页自绘假底栏」的旧坑（组件带 `env(safe-area-inset-bottom)`、88rpx + 文字，不含假状态栏）。

> **已核**：`custom-tab-bar/index.wxml` 只是 `position:fixed` + `env(safe-area-inset-bottom)` 的普通视图，`index.wxss` 全部是自有样式，**没有依赖 tabBar 特有机制**；与原生绑定的只有 `index.js:45` 的 `wx.switchTab` 和 5 处 `getTabBar()`。因此方案 B 的关键不是换组件，而是把 `switchTab / getTabBar` 这两类调用改掉（见第九节）。
> **决策**：2026-11-07 已选 **B**。

## 十、现有 18 页的处置映射（已确认可动）

### 10.1 处置原则：先改 6 个母版，再批量套用

「动 18 页」不是重画 18 张页面，而是：

```
6 个母版（重做）→ 12 页套用（中改造）→ 5 页合并/删除（轻）
```

- **母版**：今日（新）、岗位队列（新）、作业页、核销页、评估页、个人中心。这 6 个设计定了，其余页面只是「填内容」。

### 10.5 回归重点（这批改动最容易坏的地方）

1. **guard 全拒**：新键没登记 → 整组页面打不开（`auth.js:163` 直接 deny）。
2. **菜单重复**：`home` 降级后若 `workbench` 标记没同步，`menuFor()` 会同时吐出 `queue` 与旧岗位台。
3. **合并页的权限分叉**：`redeem` 一页承载遛宠/洗护/接送三种，`PAGE_RULES` 必须能按 `type` 判 `CARE/GROOM/DRIVER`，否则店长兜底核销会把三类都放开。
4. **签字快照**：`c5`/`d2` 合并或改造时 `signer_position` 不能从「登录人岗位」改成「当前页面分段」，否则 U13（调岗不改历史）失效。
5. **深链参数**：`orderDetail`/`redeem` 从队列进入必须带 `id` 与 `type`，缺参时应回队列而不是取第一单。
6. **底栏选中态**：6 个一级页 `onShow` 都要 `setSelected`，否则从详情返回后高亮停在旧项。
